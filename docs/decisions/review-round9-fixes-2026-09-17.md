## D38 · 回滚的撤销范围 = 整个窗口期（全量基线），重放才等价于「只执行一次」

| # | 决议 | 依据 |
|---|---|---|
| **D38** | 动作提交失败时：<br>① 在窗口开始前拍一份**全量**事项基线（窗口期内的一切改动都是相对它前进的）；<br>② 失败时**整体退回基线** —— 撤掉窗口期内新建的全部事项（动作派生的与用户操作派生的都在内），基线里的事项逐个整体还原；<br>③ 再按原顺序**重放**窗口期内用户的业务操作。<br>重放时把该操作当初**新建的实例 id 复用**回去（按创建顺序一一对应，目标 id 未被占用才改）。 | N1：回滚只撤 `txn.created`（动作自己派生的实例）+ 还原源事项。用户在提交期间 ACK 一条周期事项时，**那次 ACK 已经派生过一期**，它不在 `txn.created` 里；重放再执行一次 ACK，于是出现**两个下一期**（`items=3`），而且两者的计算基准不同 —— 首次按尚未提交的动作时间、重放按还原后的时间，`triggerAt` 相差恰好是失败动作的时间位移。多余提醒与周期分叉都会跟着来。<br>复核点名：**用 `touched` 过滤无关事项只能避免重放无关操作，不能消除相关操作第一次执行的副作用**；「不能只还原源事项、保留原派生结果，再调用会生成随机新 id 的业务函数」。 |

### 为什么是「整体退回」而不是「逐个撤销每个操作的副作用」

逐个撤销要求给每个操作单独记录「它改过哪些对象的哪些字段」，还要按**逆序**回滚才能处理
多个操作互相叠加的情况。全量基线的语义更简单、也更难写错：

> **窗口期内发生的一切，都是相对「动作开始前」这份基线的前进。**

退回基线 → 重放用户操作，结果就是「窗口期内的事只按用户操作的顺序发生一次」。
这也自动覆盖了之前两轮各自打补丁的点：H1（不能把期间新建的事项删掉 → 现在会**重放**出来）、
K1（用户完成本期的顺延 → 现在由重放自然重建）、M1（用户的第二次稍后 → 原样重建）。

**代价**：基线是全量浅拷贝（每个事项一份字段副本），窗口期内自动推进会（`promoteDue`、原生对账）
的写入也会被一并退回 —— 它们由时间/原生真源驱动，下一拍会自行重算。这些都在窄窗口内，可接受。

### 为什么要复用派生实例的 id

重放会重新执行派生（`spawnNextInstance` 生成**新** id）。若用户在窗口期内还操作过那个刚派生出来的实例
（例如把下一期改到 3 小时后），重放第二次执行该操作时会**找不到目标**而静默丢失。
所以记录该操作当初新建的实例 id，重放后按顺序改回去 —— 后续操作就能命中同一个实例。

   - 把 D30–D38 的修复**全部**按语义逐条回退 → **失败 63 项**。

     **失败 11 项**，症状与复核探针逐条一致：
     `N1 恰好一个下一期（首次执行的副作用必须已被撤销） — next=2 items=3`、
     `N1 重载后：下一期的时刻仍按有效状态 — [1790220120000, 1790212920000]`（相差正好是失败动作的 2 小时位移）、
     `N1c 重载后：本期已完成、恰好一个有效下一期 — [["A","archived"],["N","waiting"],["N","waiting"]]`、
     `N1b 重载后：派生实例的修改仍在、且只有一个下一期 — […,["?","waiting",…]]`。

   - 只回退提交闸门（I1）失败 17 项；只回退动作隔离（J1）失败 56 项。

   - 「周期事项原生稍后提交中 → UI ACK → 稍后失败 → ACK 保存成功 → **重载**」后，
     **恰好一个下一期**、且它的时刻按**有效状态**计算（与基线时刻同日同分，不带失败动作的位移）、

     回滚重放后修改仍在、id 不变、仍只有一个下一期）；
   - 无关事项不被重复重放（M1d），以及 M1/K1/I1/J1 全部回归。
