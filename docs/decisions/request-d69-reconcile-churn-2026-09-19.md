# 待裁决 · D69：对账每被触发一次就全量重写所有闹钟

> **2026-09-19 状态更正**：下文保留发现时的历史诊断，不代表当前源码。
> 四阶段交接 C 已落实 `nativeSyncInFlight/nativeSyncPending` 串行合并、
> `deferNativeSync` 内部保存隔离、`alarmSignaturesCache` 差量排程与有界日志。
> 因此“仍未实现、每轮全量重排”已过时；但原 1Hz 来源与最新候选实机长期效果未获完整证据，不能宣称 D69 全场景闭环。

## 一句话

`reconcile` 是**全量重写**：每被触发一次，就把**所有**闹钟重新 `setAlarmClock` 一遍
（同一 `PendingIntent` 被替换，所以功能上「幂等」），并为此写 5 条台账。
这在功能上没错，但它有两个不便宜的后果：**诊断台账的可用历史被压到几十秒**，
以及**每次对账都要同步写盘 + 调 AlarmManager**。

## 这是设计选择，不是实现疏漏

`lib/native-reminders.js:571-572` 的注释是明写的：

> 排程本身幂等（同一 request code 的 PendingIntent 会被替换），因此对 desired 全量重排，
> 只把「上一轮排过、这一轮不再需要」的 id 撤掉。

## 现象证据（真机 vivo V2238A / Android 16，2026-09-19 10:04–10:09）

| 观测 | 值 | 取法 |
|---|---|---|
| 台账被**同一个闹钟**的 30 轮重排刷满 150 条上限 | `cancelled`/`requested`/`item`/`unfreezerScheduled`/`scheduled` **各 30 条**，全部 id `1354819241`（交房租） | `run-as <pkg> cat shared_prefs/alarm_trace.xml` 逐条解析 |
| 轮距 | **1004 ms**（29 轮跨 29.13 s） | 同上，`at` 字段差分 |
| 被重排的闹钟目标时刻**恒定** | `triggerAt≈1789908660088`（2026-09-20 20:51），`delayMs` 每轮减 1000 | 台账 `detail` |
| **风暴期间没有任何闹钟真的到点** | `*walarm*:…ACTION_TEST_ALARM` 累计 **2 次**、`AlarmRingService` 3 次、`AlarmActivity` 1 次 | `dumpsys alarm` → `Alarm Stats: u0a190:space.alliswell.inbox` |
| **页面没有重载** | `performance.timeOrigin` = 10:03:46，观测时 `performance.now()` 已 818 s；`__probeInstalled` 在同一 page 上下文里始终有效 | CDP `Runtime.evaluate` |
| 原生**没有**向 WebView 推事件 | Java 侧全仓 `notifyListeners` / `evaluateJavascript` 命中 **0** | `grep` 全 `android/app/src/main/java` |
| 风暴自身起止 | 至少 10:08:15 → 10:09:20 连续（窗口上限 30 s，起点被截断），之后自行停止 | 两次拉取比对 |

### ⚠️ 触发条件**未定位**（这一点必须说清）

4 次受控复现（前台 60 s、后台息屏 75 s 含一次真实响铃、我的页 + 自检面板打开 + 后台 60 s）
**均未复现**。上面那份证据全部来自**被动撞见的一次现场**。

**能确定的**是机制（全量重排 + 5 条台账/轮）；**不能确定的**是那一次是什么以 ~1 Hz 触发了对账。
JS 侧有 **22 处**调用 `queueNativeReminderSync()`（含 `save()` 内、`onResume` 回调内、
`visibilitychange → tick()` 的提示路径内），因此「任何一条通路被反复触发」都会产生这个现象 ——
**这正是要裁决的点**：产品要不要为「对账被反复触发」付这笔开销。

### 已定位的**放大器**（代码级，可指名到行）

不止「有一条通路被反复触发」这一件事 —— 一次前台事件会**放大成两次对账**：

```
Capacitor App 插件的 appStateChange(isActive)
  ├─ lib/native-reminders.js:1019  → drainAlarmActions → handleAlarmAction → queueNativeReminderSync()   (app-core.js:4208)
  └─ lib/native-reminders.js:1094  → handlers.onResume                        → queueNativeReminderSync()   (app-core.js:5039)
```

两条通路各自 `await` 原生往返，**落在 `queueNativeReminderSync` 的 80 ms 去抖窗口之外**，
于是同一次「回到前台」被记成两轮对账 → 两轮**全量重排**。
这与 2026-09-19 第二次观测完全吻合：重排**成对出现**，对内间隔 0.25–0.9 s
（10:22:38.175+38.423 · 10:22:46.587+46.934 · 10:22:54.526+54.904），对间约 8 秒。

也就是说：**常态下每做一件事就重排所有闹钟两遍**；那一次 1 Hz 的连续风暴是同一个放大器
被某个高频前台事件驱动了约 5 分钟。放大器的位置已经清楚，缺的只是那次的驱动源。

### 但**不要**据此认定「1 Hz 就是 `appStateChange` 在抖」——探针实测把它排除了（至少那 436 秒里）

2026-09-19 在判定用的那一轮（r3）注入了探针（包住插件方法记调用栈 + 记定时器注册 +
监听 `appStateChange`），全程 **436 s**：

| 观测 | 值 | 含义 |
|---|---|---|
| `scheduleAlarm` 累计 | **10 次**（≈ **0.02 次/秒**） | 观测期内**没有**风暴；对照风暴期是 1 次/秒 |
| `queueNativeReminderSync` 的 80 ms 去抖注册 | **12 次** | 即 12 次「请求对账」——放大器确实在工作，但频率很低 |
| `appStateChange` 事件 | **2 次**（10:33:36 转后台、10:39:06 回前台） | 在这 436 s 里它**没有抖动** |

⇒ 结论分两层：

1. **放大器是代码级事实**（两条通路各自 `await`，去抖兜不住）—— 它解释台账里**成对出现**的重排
   （r2/r3 窗口内对内间隔 0.22–0.94 s）。
2. **那一次 1 Hz 连续风暴的驱动源仍未定位** —— 上述 436 s 里 `appStateChange` 只发生 2 次，
   所以「Activity 反复 resume」这条假设**不能被当作已证结论**。它只是候选之一。

## 两个后果

**① 诊断台账的可用窗口 = 150 ÷ (5 × 闹钟数) 轮。**

`AlarmTrace.record` 只保留最后 150 条（`AlarmTrace.java:17`）；一次「重排既有闹钟」写 5 条。
一个闹钟时窗口 ≈ **30 轮**；对账密集到 1 秒一轮时，台账里只剩 **30 秒**历史 —— 任何更早的证据被静默丢弃。

**这不是理论问题**：本次 D68 真机验证脚本第一版就是**这样崩的** —— 它每 3–5 秒读一次台账，
等到最后还是读到空表（`ParseError: no element found: line 1, column 0`），
而它要等的 `ringStarted` 早已被后续重排挤出。脚本现在改成累积式（`Ledger`），
但这属于**绕开**，不是修复。

**② 开销：每轮 5 次 `SharedPreferences.commit()` + 2 次 AlarmManager 调用。**

`commit()` 是同步写（含 fsync），且**每次都重写整个 150 条 JSON**（实测该文件 31 KB）。
1 秒一轮 = 每秒重写约 150 KB 并落盘，外加 `setAlarmClock` + `setAndAllowWhileIdle`。
对一块手机电池来说这不是零成本；对一个「响不响」还没收口的项目来说，这是**在没有收益的地方花电**。

## ① 要决定什么

**三件事**：① 是否把对账改成「**只在计划真的变化时才重排**」；
② 是否**先单独把诊断台账的容量问题解决掉**（它是取证能力）；
③ 是否**合并同一轮前台事件引发的重复对账**（放大器已在代码层指名，见下）。

## ② 可选方案与利弊

| 方案 | 做法 | 好处 | 代价 / 风险 |
|---|---|---|---|
| **A 维持现状** | 不改代码 | 零风险 | 取证窗口几十秒；密集对账时白耗电。**后续每一次真机验证都要靠脚本自己累积兜住** |
| **B 台账扩容 / 分层** | `AlarmTrace` 上限 150 → 比如 2000；或按 token 保留「首末事件」 | 直接恢复事后取证能力；**不动任何排程语义**；改动集中在 1 个文件（`AlarmTrace.java`） | 每次 commit 的 JSON 变大（成正比），若对账仍密集则写盘更贵 —— 所以严格说 B 与 ② 是「取证」与「开销」两件事，B 只解决取证 |
| **E 去抖合并（合并同一轮的前台事件）** | 让上面那个放大器的两条通路**共用一个排队标志**（或在途请求内再次请求只标记「重跑一次」），使一次前台事件最多变成一轮对账 | 直接砍掉常态下一半的无谓重排；**不动 reconcile 的语义**（该排的仍然排）；改动集中在 `queueNativeReminderSync` 一处 | 去抖窗口从 80 ms 延长会让「刚刚改期的闹钟」晚几十到几百毫秒才落进系统 —— 对闹钟档要确认这个延迟可接受（个人认为可接受：用户改期的动作本身不要求亚秒级生效） |
| **C 对账幂等化** | `reconcileAlarms` 比对「上一轮已排、且 `id + triggerAt + 内容版本` 未变」的项就**跳过** `scheduleAlarm`，只撤多余的 | 根治开销；台账自然不再被打转 | **重排目前同时承担「PendingIntent 被系统清掉后补排」这个职责**。跳过它必须补一个**回读校验**（`dumpsys alarm` / `AlarmManager.getNextAlarmClock` 之类的可回读证据），否则风险从「多排」变成「**漏排**」—— 而漏排正是这个项目最贵的失败形态（H-08：用户收不到闹钟） |
| **D B + C 一起** | | 一次收口 | C 的风险原样存在；且两件事的验收方式完全不同（B 不需要真机链路验证，C 必须重跑整条投递链路） |

## ③ 推荐

**先做 B + E**（各自改动都很小、都不碰排程语义），**C 另立一轮**单独裁决与真机验证。

如果只能动一件事，就动 **B**（它换回的是后续所有真机验证的取证能力）。

## ④ 为什么

1. **B 是取证能力，C 是性能优化。** 这个项目所有结论都必须「绑可复现证据」，而台账就是真机上唯一的证据源。
   窗口只剩 30 秒时，**任何需要等待的验证（自动静音要等 5 分钟）都无法留下证据** ——
   这次 A-1 验证差点因此失败。取证能力是后面所有验证的地基，优先级高于省电。
2. **B 与 E 都不碰排程语义。** B 只改「记多久」，E 只改「同一轮内合并几次请求」 ——
   两者都不改变「什么条件该排、排到哪个时刻」，因此**不需要重跑投递链路验证**
   （D48 的教训是注入过的路径证明不了生产路径，而这两项与投递无关）。
   E 的收益是常态的：**每做一件事少一半无谓重排**，而那正是我们每天都在付的成本。
3. **C 会把「多排」换成「漏排」的风险敞口。** 现在的全量重排有一个没说出口的好处：
   系统的闹钟被清掉（重装、force-stop、厂商清理）后，**下一次对账一定会补回来**。
   要跳过重排，就得先有「怎么知道它还在」的回读手段与对应的补排分支 ——
   这是一条独立的、必须真机实测的改动，**不该和改动面更小的 B/E 绑在一轮里**。
4. **A 不可接受**，理由同 1：它把「取证」这件事永久性地外包给每个验证脚本自己去兜，
   而脚本一旦写错（这次就是），失败形态是「**看起来跑完了**」而不是报错。

## 需要花心思 vs 点头即可

| | 项 |
|---|---|
| **真需要花心思的** | **C 要不要做、以及「跳过重排」靠什么回读证据来保证不漏排** —— 这需要一次独立的真机方案设计 |
| **照推荐点头即可的** | **B**（台账扩容 / 分层）与 **E**（去抖合并），以及**认可 D69 的存在**（即：接受「对账被反复触发 → 全量重排」是一个要处理的已知问题，而不是偶发现象） |

## 附录：方案 B / E 的具体形态（若采纳，落地时再定稿）

**B —— 台账扩容 / 分层**

- `AlarmTrace.record` 的上限从 150 提到 2000（≈ 每次 commit 的 JSON 从 31 KB 到 ~400 KB，
  单次写盘变慢但对账不再密集时总写入量反而下降）；
- 或更省的形态：**按 token 保留首末**（同一 token 只留第 1 条与最后 2 条），
  这样「排了没」「跑到哪一步」「有没有静音」三件事都还在，而 30 轮重排只占 3 条。
- 无论哪种，`AlarmTrace` 仍是「有界、不含正文」的取证文件，不涉隐私口径变更。

**E —— 去抖合并**

- 现状：`queueNativeReminderSync()` 是「清掉旧 timer、再排一个 80 ms 的 timer」。
  当**两条通路各自 `await` 原生往返**时，第二次请求落在 80 ms 之后，于是去抖失效 → 两轮对账。
- 形态一（最小）：加一个 `nativeSyncInFlight` 标志 —— 在途期间到达的请求只置
  `nativeSyncDirty = true`；本轮结束后若 dirty 则再跑**一轮**（不是每来一次跑一次）。
- 形态二：把去抖窗口从 80 ms 提到 ~400–600 ms。改动更小，但会让「刚刚改期」晚一点落进系统。
- 建议形态一：它把「同一个前台事件触发的 N 次请求」压成「1 次 + 最多 1 次补跑」，
  既不引入固定延迟，也不会丢掉「在途期间真的有新改动」这件事。
