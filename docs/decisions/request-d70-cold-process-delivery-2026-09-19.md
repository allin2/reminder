## 1. 一句话说清要决定什么

**闹钟在「App 被系统杀掉之后」根本不会响**，而且**不会补投**。
原因是 ColorOS 禁止 App 被闹钟唤醒时自己重新启动。这个开关在系统设置里，**用户不去开就一直漏**。

要决定的是：**要不要让用户知道这件事、以及用什么方式让他能修好。**

## 2. 事实基础（全部来自上一轮真机一手证据，可复算）

| # | 事实 | 证据 |
|---|---|---|
| F1 | 排程**没丢** —— kill 前后、触发前 5s，该 alarm 始终在系统队列且排第 1 | `20260919-oppo-cold-diag/diag.json` 时间线 A–D |
| F2 | 系统**确实发出了**闹钟，AOSP 层**批准**了 FGS 启动 | logcat `V/AlarmManager: sending alarm` + `ActivityManager: Background started FGS: Allowed` |
| F3 | 是 **ColorOS 否决**的，服务与广播两条路都被拦 | logcat `OplusAppStartupManager: prevent start … Type ssfa` × 3 |
| F4 | **有牙齿的对照组**：同路径同屏幕状态，唯一变量 = 进程存活 | 热进程 `prevent start` = 0（成功）/ 冷进程 = 3（无投递） |
| F5 | 进程**从未被拉起**（触发后 `pid` 始终为空） | `diag.json` 时间线 E–I（观察 60s） |

### 2.1 P1 的代码级根因（本轮新发现）

`lib/native-reminders.js` 的**单次提醒台账**是三态（键 = 「原定触发点」）：

```
scheduled  已请求系统投递、还没有送达证据 → 不重排也不补发（无法判定是否送达）
delivered  有真实送达证据 → 终态，永不再打扰
cancelled  排程被成功撤销 → 视同「从未排过」
```

而 `lib/native-reminders.js:340` 是：

```js
if (rec && rec.state === "scheduled") continue;
```

**冷进程被拦 ⇒ 永远拿不到送达证据 ⇒ 状态永远停在 `scheduled` ⇒ 每次对账都 `continue` ⇒ 永不补投。**

这正是真机上「完全不响且不补投」的**代码级解释**。注释自己写着「**无法判定是否送达**」——
项目**早就认识到这个状态**，只是它当前的后果是**静默放弃**，而不是「告知用户」。

> 这条同时解释了为什么 P1 不是「偶发投递失败」，而是**一旦命中就永久失效**。

## 3. 本轮只读探测的决定性发现：这条路只有「一个可用判定源」

在写规格前，先确证「能不能读到自启动授权状态」—— 这决定方案形态。真机只读探测结果：

| 探测项 | 结果 |
|---|---|
| `settings list secure`（720 行）· `global`（637）· `system`（834）**全量扫描** | ❌ **无任何「自启动 / 关联启动」相关键**（命中项全是 boot 计时、OTA、动画速度等无关键） |
| 本包 **54 条 appops 全量** | ❌ **无对应 op**；且相关的 `RUN_ANY_IN_BACKGROUND` / `START_FOREGROUND` / `BACKGROUND_START_ACTIVITY` / `SYSTEM_ALERT_WINDOW` **全部 `allow`** |
| AOSP 标准接口 | ❌ 无自启动授权查询 API |

**结论：从标准 Android 接口看，这个应用一切正常；ColorOS 的拦截完全发生在标准接口之外，应用内读不到。**

### 3.1 由此排除的两个方案形态

| 被排除的形态 | 为什么不行 |
|---|---|
| **按 D68-b 模式做「状态告警」**（读状态 → 报断链） | `homeNoticeVerdict()` 的核心纪律是**「只在能确证断链时出声」**，且明确把「未定」一律返回 `null`。自启动状态读不到 ⇒ **永远无法确证** ⇒ 这个形态从根上不成立 |
| **复用 `lastAlarmDelivery` 判定** | 它的写入者是 `AlarmTestReceiver`（`AlarmTestReceiver.java:129` 等）—— **正是被 ColorOS 拦掉的那个组件**。失败时它根本不执行，记录**不会更新** ⇒ **它检测不到本缺陷**。它只反映「上一次成功投递」，不是「上一次尝试」 |

### 3.2 唯一可用的判定源

**跨进程边界的事件特征**：

| 事件 | 写入者 | 写入时机 |
|---|---|---|
| `scheduled` | `AlarmScheduler.java:129` / `SystemBridgePlugin.java:1017` | **排程侧**（进程还活着时） |
| `received` / `delivered` | `AlarmTestReceiver.java:129` 等 | **接收侧**（进程被拉起时） |

⇒ **「有排程记录、但始终无送达证据」是一个天然的自证特征**，且**不依赖任何厂商接口**。

**更省事的是**：§2.1 的三态台账 `item.reminderEvents` **已经是这个判定的现成载体** ——
`state === "scheduled"` 且键里的「原定触发点」已过期，就是「未送达」。
**不需要新解析原生台账 `alarm_trace`。**

### 3.3 已有零件盘点（缺口只有一个）

| 零件 | 现状 |
|---|---|
| 打开厂商自启动设置页 | ✅ **已实现** `SystemBridgePlugin.openAutoStartSettings`（10 个厂商候选组件含 ColorOS 两条，全失败退回应用详情，返回实际落点 `component`）；Web 侧已在自检面板调用（`app-core.js:4882`） |
| 「未送达」判定源 | ✅ **已存在**（三态台账，§2.1） |
| 首页告警容器 | ✅ **已存在** `#homeNotice` + `homeNoticeVerdict()`（D68-b，现有 4 分支） |
| 排程时前置引导的模式 | ✅ **已裁决并落地**（A-2，D68 第一层） |
| **把「未送达」判定接进首页 + 首用引导** | ❌ **这是唯一缺口** |

> **所以 ① 不是「新建一套引导」，而是「给已有的告警机制加第 5 档 + 加一个首用引导」。**
> 实现风险远低于从零开始 —— 但它有一个**语义变更**（见 §5 Q1），必须由你拍板。

## 4. 建议的落地形态

### 4-1 首页第 5 档（事后自证）

`homeNoticeVerdict()` 新增一档，**排在现有 4 档之后**（前 4 档都是更直接、更能自证的断链）：

```
① 总开关关  →  ② 通知权限未给  →  ③ 原生桥未就绪  →  ④ 对账失败  →  ⑤ 提醒未送达（新）
```

**判定条件（严格）**，全部满足才出声：

1. 台账里存在一条 `state === "scheduled"` 的提醒记录；
2. 其「原定触发点」+ **宽限期** < 当前时刻（即：早该送达了）；
3. 该事项**仍然活跃**（未归档 / 未删除）—— 用户已经处理掉的不再唠叨；
4. 该项**没有被用户主动延后屏蔽**（`dismissedUntil` 未生效）。

**返回 `null`（不出声）的所有情形**：触发点未到、已 `delivered`、已 `cancelled`、事项已归档、读不到台账、宽限期未过。
⇒ 与 D68-b 同一条纪律：**未定一律闭嘴**。

### 4-2 排程时首用引导（事前引导）

复用 **A-2 的成功模式**（D68 第一层已裁决并落地：「在用户还在 App 里、还愿意动手的时刻说」）：

**用户新建第一个「重要档 / 闹钟级」事项时，一次性引导**（可「不再提醒」）。

- 不在首次进入 App 时弹 —— 那时用户还没有需要准点响的事项，只会被跳过；
- 在「他要一件必须准点响的事」这一刻说，3–4 步的成本才成立；
- 这也正好补上 **D25 / A-01「重要档 = 闹钟级」这个已作出的承诺**的前置条件。

### 4-3 动作落点

两档都调**已有**的 `openAutoStartSettings()`，并把返回的 `component` 记进诊断台账
（该函数已支持返回实际落点，便于事后确认「引导到底把用户送到了哪一页」）。

点击失败（厂商页打不开）时，**退回图文指引**，不得静默失败。

| # | 问题 | 选项与利弊 | 我的建议 |
|---|---|---|---|
| **Q3** | 宽限期取多长（多久没送达算「确定漏了」）？ | (a) 2 分钟 —— 快，但系统闹钟在极端省电态下本就可能延迟数十秒，**有误报风险**<br>(b) 30 分钟<br>(c) **下一次打开 App 时**（不设固定值，以「用户已回到 App」为观察点）<br>(d) 24 小时 | **(c)**。理由：判定的目的**不是**统计延迟，而是**在用户能看到的时候告诉他**。以「回到 App」为观察点，天然避免了在用户看不见时做无意义的判定，也绕开了「多久算迟到」这个没有正确答案的问题。(a) 会被正常延迟打成误报 —— 而误报的代价比漏报更贵，它会让**整条告警失去可信度** |
| **Q4** | 判定为「未送达」之后，除了告知，**要不要允许补投一次**？ | (a) 只告知，不改投递行为（最小改动，绝不重复打扰）<br>(b) 告知 + 允许补投一次<br>(c) 告知 + 补投，且把该事项在首页提到最前 | **(a) 起步**。理由：(b)/(c) 动的是**投递语义**，会牵出「补投算不算重复提醒」「补投又失败怎么办」等一串新问题；而 (a) 已经把**用户不知情**这个最坏后果消灭了。等 ① 跑通、观察到真实命中率之后再单独裁决补投 |

## 6. 必须诚实标注的不确定性与依赖

| # | 事项 | 状态 |
|---|---|---|
| **U1** | **与 D69 的真实依赖**：台账（原生 `alarm_trace`，150 条有界环形缓冲）在 D69 未修前会被对账以约 1Hz 的全量重排冲刷。**但本方案的判定源是三态台账 `item.reminderEvents`（存在 `state.items` 里、随业务数据持久化），不是原生环形缓冲** ⇒ 判定本身不受 D69 影响。**受影响的是「诊断面板里的事后取证」** | ⚠️ 判定不受影响；取证受影响 |
| **U2** | `delivered` 的**全部**写入点未逐一核验。若存在「已送达但 `delivered` 未写上」的路径，**会产生误报** | ❌ **未验证 —— 实现前必须先核**（这是 Q1 选 (a) 的前置） |
| **U3** | `openAutoStartSettings` 的 10 个候选组件在 **ColorOS 16 上能否真正打开目标页**未实测（上一轮「厂商设置页无法从 adb 打开」已记 `NOT_PERFORMED`） | ❌ **未验证**，需一次真机点击 |
| **U4** | 「未送达」的**归因**：ColorOS 拦截是**当前已知最可能**的原因，但不是唯一可能（如系统正常回收后拉起失败）。**文案不得断言单一根因** | ⚠️ 已写入文案纪律 |
| **U5** | 真实「用户从最近任务划掉 App」路径无法模拟（`am kill` 在 ColorOS 无效、`kill -9` 非真实路径）⇒ **本缺陷在真实操作下的命中率未知** | ⚠️ 已知局限 |

### 文案纪律（必须遵守，与 D59 的教训方向相反）

D59 的纪律是「**不得把『响了但没亮屏』反着报成『完全静默』**」。
本场景**确实**是全静默（`AlarmRingService` 未启动，无声无振无通知无界面），但**归因不能说死**：

- ✅ 「上一次提醒**没有送达**。系统可能限制了应用在后台启动。」
- ❌ 「闹钟不响」/「自启动没开」/「系统杀了你的应用」

「不说闹钟不响」这条通用纪律在**归因不确定**时仍然成立；本场景可以（且应该）**如实陈述「没有送达」这个已确证的事实**，但不给它一个猜测的根因。
