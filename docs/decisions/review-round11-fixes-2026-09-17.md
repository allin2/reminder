## D40 · 重放必须从基线状态按顺序执行：删除也要按操作顺序发生

| # | 决议 | 依据 |
|---|---|---|
| **D40-a** | 回滚的第 2 步里，**纳入还原范围的基线事项若已被删除，先按基线把它恢复出来**（再交给重放）。删除是**操作顺序里的一步**，由重放按原顺序执行 —— 不能提前到更早的操作之前生效。最终状态仍然是用户要的「已删除」。 | **Q1**：回滚只还原「当前还在」的事项，对被删掉的那条直接 `return`（注释认为「删除会在重放时重做」）。于是：用户 ACK 本期（派生下一期）→ 删除本期 → 提交失败 → 回滚时本期仍处于删除态 → 重放 ACK 时**找不到源事项**、直接跳过 → 那一期派生出来的下一期再也回不来。实测 `回滚后：items=[]`、`重启后：items=0` —— 用户只删了本期，周期却被弄断。<br>复核点名：**重放必须从正确的起始状态按顺序执行；不要把「最终应删除」提前到所有历史操作之前。** |
| **D40-b** | 「参数指向的事项」这项归属兜底**必须包含字符串 id**，并且要在**调用之前**认领。 | 归属兜底原先只看对象参数，而 `deleteItem(id)` 传的是字符串 —— 调用之后该 id 已经不在 `state.items` 里，**认不出「被删的那一条」**，它因此落在还原范围之外，D40-a 的恢复逻辑根本不会被触发。所以两处要一起改：调用前认领 + 认字符串 id。 |

**为什么恢复而不是「先重放、后删除」**：重放是按日志原顺序执行的（ACK → 删除），
所以只要**起始状态**是正确的基线，顺序天然就对。恢复出来的对象是**新建的**
（原对象已不在 `state.items`），后续操作全部按 **id** 解析（D39-b 的机制），因此不受影响；
但也意味着**调用方手里的旧引用会变成孤儿**，测试与调用方要按 id 从 `state.items` 取。

**副作用与边界**：
- 只对**纳入还原范围**（`txn.targetId` ∪ 各条记录的 `touched`）的已删基线事项做恢复 ——
  未纳入日志的删除（未记录入口、外部同步）**不会**被复活（保持 fail-safe）。
- 恢复会让「本期被删、下一期保留」这种组合重新成立；若用户删掉的是**派生出来的那一期**，
  它不在基线里，不会被恢复，重放那次删除也会再删一次（有专项回归守着）。
- 恢复会把事项**追加到 `state.items` 末尾**（列表渲染按时间/优先级排序，不依赖数组顺序）。
