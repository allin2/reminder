## D39 · 撤销范围按「动作动过的 ∪ 重放会重做的」界定；日志参数按 id 寻址

| # | 决议 | 依据 |
|---|---|---|
| **D39-a** | 回滚的撤销范围界定为**动作动过的 ∪ 重放会重做的**：<br>① 只撤**台账里记过**的新建（动作派生的 + 用户操作派生的）；<br>② 只还原**会被重放再次改写**的既有事项（+ 动作自己的目标）；<br>③ 其余写入（未纳入日志的入口、定时推进、原生对账）**保留原样**。 | **P1-A**：「删掉一切不在基线里的事项」要求日志 100% 完整 —— 真实表单新建入口没有进日志，用户在等待闹钟提交期间建好的事项连同提醒被静默删除（`回滚后：[original]`）。把「漏记一个入口」的后果从**数据丢失**降级为**保留未记录写入**。 |
| **D39-b** | 操作日志的参数**自足化**：指向现有事项的参数记成 `{__itemRef: id}`，重放时按 id 重新解析；其它对象参数存一份值快照（深拷贝）。指向的事项已不存在时跳过该条。 | **P1-B**：回滚会**重建**派生实例（id 复用、对象是新的）。日志里存的是当初那个对象的引用，后续 `applyItemEdit` 就写到已经离开 `state.items` 的旧对象上 —— `回滚后 N.title=每周复盘`，用户保存的标题/备注静默丢失。 |
| **D39-c** | 真实新建入口纳入日志：抽出 `applyNewItem(id, fields)`（稳定 id + 已解析字段快照），`saveItemFromForm` 的新建分支改为记录它。 | 复核建议「将实际新建入口…纳入完整操作日志，记录已解析字段和稳定 id」。`id` 由调用方给定 ⇒ 重放沿用同一 id，后续针对它的编辑/删除都能命中。 |
| **D39-d** | 归属判断兜底：`touched` = 版本号变化的事项 **∪ 参数指向的事项**。 | 归属判断依赖「改事项就 `bumpRev`」（L04 的既有约定）。万一某个入口忘了推进版本，这条兜底保证它不会被漏掉 —— 漏掉的后果是「回滚不还原、重放又执行一遍」。 |

**为什么不用「按 id 反向解析」以外的办法**：也可以把编辑日志改成只存 id 与字段值，
但那需要给每个入口逐一定义「哪些参数是事项、哪些是值」；`recordArg` 用「参数此刻是否
就是 `state.items` 里那个对象」来判定，对所有入口一致生效，新增入口也不用再改。

**仍然依赖的约定（写进代码注释与记忆）**：
① 凡是用户可触发、会改事项的入口，都要用 `wrapUserOp` 包一层；
② 参数里指向事项的对象**必须**是 `state.items` 里的那个对象（否则会被当成值快照，
重放时按快照重建 —— 对「新建」是正确的，对「编辑既有事项」则会丢失关联）；
③ 改事项就要 `bumpRev`。

> **⚠️ 第十一轮更正（D40，2026-09-17）**：D39-a 的还原范围（只还原会被重放改写的事项）
> 仍漏了一种情形 —— **被窗口期删掉的基线事项**。原实现直接跳过（认为「删除会在重放时重做」），
> 于是更早的 ACK 在重放时找不到源事项、被整体跳过，它派生的下一期随之丢失（Q1）。
> 现改为：纳入还原范围的已删事项**先按基线恢复**，删除由重放按原顺序执行。
> 另：归属兜底原先认不出字符串 id 形式的删除目标（`deleteItem(id)`），也已修正。
> 见 `review-round11-fixes-2026-09-17.md`。
