# 提案 · 闹钟档的界面可达性与「停不下来」问题

> **本文件是提案，不是裁决。** 按本项目约定：**未获明确裁决前不实现任何内容，代码一行不动。**
> 需要产品所有人回答的问题集中在文末，编号 **Q1–Q6**，可直接按编号答复。

## 0. 一句话

D59 之后闹钟档在「无通知权限 + 息屏」下**会响会振**，但**界面起不来、通知栏也没有** ——
用户面对的是「**只闻其声、不见其屏、也停不下来**」，最坏情况响到 **6 小时**上限。
本提案要决定的就是**这一格还接不接受**，以及不接受的话走哪条路。

## 1. 现场事实（先勘清，附证据）

### 1.1 实测到的样子

| 要素 | 无通知权限 + 息屏锁屏时的实测 | 证据 |
|---|---|---|
| 铃声 | ✅ 响（`state:started usage=USAGE_ALARM`，持续 3 分钟以上） | D59 真机记录 |
| 振动 | ✅ 振（波形 `{0,800,400,600}` 周期持续） | 同上 |
| **屏幕** | ❌ 不亮（`mWakefulness` 全程 `Asleep`） | 同上 |
| **界面** | ❌ 未拉起（`dumpsys activity activities \| grep AlarmActivity` = **0**） | 同上 |
| **通知栏** | ❌ 无（无通知权限，`notify()` 空操作） | 同上 |
| **停止入口** | ❌ **只剩「解锁并打开 App」** | D63 |

台账里同时留了 `launchLikelyBlocked  no SYSTEM_ALERT_WINDOW` 与
`launchRequested  not proof of visibility` —— 即「我申请了，但我知道大概率被拦」。

### 1.2 界面为什么起不来：BAL（后台启动 Activity 限制）

官方（[secure-bal](https://developer.android.com/guide/components/activities/secure-bal)）给的
**放行清单**是有限枚举，逐条对照我们的处境：

| 官方例外 | 我们能否拿到 |
|---|---|
| 应用有**可见窗口** | ❌（息屏 + 后台，本来就不满足；这是结果不是手段） |
| 应用是当前输入法 | ❌ |
| **活动由「系统发送的 PendingIntent」启动** | ⚠️ **理论可达，但本项目的路径上未确证**（见 §3-Q3） |
| 应用已获 **`SYSTEM_ALERT_WINDOW`** | ⚠️ **可拿**，但要用户去设置里手动开（本机实测当前为 `ignore`） |
| 应用已获 `START_ACTIVITIES_FROM_BACKGROUND` | ❌（signature/privileged，第三方拿不到） |
| 绑定到「已获准启动后台活动的服务」 | ❌ |
| 由**启动器**发起 | ❌ |
| 来自**操作系统核心部分** | ❌ |

**关键否证（本机实测）**：闹钟响铃期间 `mediaPlayback` **前台服务已经在跑**，
`launchRequested` 之后 `AlarmActivity` 计数**仍为 0** ⇒
**前台服务不是 BAL 例外**。这条排除了「只要服务活着就能拉起界面」的想当然。

> ⚠️ **顺带更正我们自己写错的一句话**：`AndroidManifest.xml` 里 `SYSTEM_ALERT_WINDOW`
> 的注释写着「第三方应用**唯一**能拿到的就是 SYSTEM_ALERT_WINDOW」。**这句不准确** ——
> 官方清单里「由系统发送的 PendingIntent 启动的活动」对第三方同样可达（通知点击就是它）。
> 这句话是 Q3-a 那一轮写下的，会误导后来的判断，建议同批改掉。

### 1.3 现状实现的关键细节（决定候选方案怎么做）

| 位置 | 现状 |
|---|---|
| `AlarmScheduler.java:53` / `SystemBridgePlugin.java:599` | 闹钟的**操作** PendingIntent 是 **`getBroadcast`**（到点先派给接收器） |
| `AlarmScheduler.java:72` / `SystemBridgePlugin.java:612` | `AlarmClockInfo` 的 **`showIntent`** 才是 `getActivity`，但它的用途是**状态栏闹钟图标**，不是自动拉起 |
| `AlarmTestReceiver.java:238` | 真正的拉起是接收器里**自己** `context.startActivity(...)` ⇒ **发送方是我们自己 ⇒ 不构成「系统发送」** |

## 2. 候选方案与利弊

### A 组 · 照推荐点头即可（低风险、依据成熟、不依赖任何不确定的拉起路径）

#### A-1 闹钟档加「自动静音上限」

**做什么**：闹钟档响铃超过 N 分钟后**自动停止声振**（N 可配，默认建议 5–10 分钟），
停止后仍保留「响过但未确认」的状态，等用户下次打开 App 再处理；6h 的 `MAX_AGE_MS` 仍保留作最后防线。

| 利 | 弊 |
|---|---|
| **一发消灭最坏后果** —— 不再有「响 6 小时且关不掉」 | 用户明确未确认的闹钟会被静音（用「未确认」状态 + 复访提示补偿） |
| **零权限、零不确定性**：不依赖 BAL、不依赖任何开关 | 与「响到用户确认为止」的直觉有出入，需要一次产品裁决 |
| **就是行业成熟做法**：AOSP DeskClock / Google Clock 的「静音时长（Silence after）5/10/15/30 分钟」 | |
| 与用户口径一致：「不需要有自己单独的逻辑」 | |

#### A-2 排程时前置检查：把「无通知权限」在闹钟档升为**阻断级**

**做什么**：用户给「关键/重要」档排一条走闹钟的提醒时，**排程那一刻**就查通知权限；
缺权限就**就地**说清「这一档要靠通知权限才能亮屏 / 才能停」，并给一键去授权，
而不是等投递失败后在自检面板里翻出来（那正是 D67 说的「该说的没说」）。

| 利 | 弊 |
|---|---|
| **在最能挽回的时刻说**（用户还在 App 里、还愿意点） | 多一步打断，可能让「快速记一条」变慢（可用「不再提醒」缓解） |
| 不需要任何新权限；不依赖任何不确定的路径 | |
| 与 D67 同一条纪律：**降级必须被说出来，且要在用户能行动的时候说** | |

> A 组的共同特征：**它们都不试图让界面在无权限下凭空出现，而是把「无权限」当作一个
> 必须被用户知道、并尽快消除的状态** —— 这也是成熟闹钟产品的实际做法（Google Clock、
> TickTick 闹钟提醒都把通知权限视为**必需**，并在缺失时强引导）。

### B 组 · 真正需要花心思（要先验证，再裁决）

#### B-1 把「拉起界面」交给系统：改走**系统发送的 PendingIntent**

**做什么**：官方清单里有一条我们**没有用上**的例外 ——
「活动由**系统发送的 PendingIntent** 启动」（通知点击就是靠它）。
思路是让**系统**来发这个 PendingIntent，而不是我们的接收器自己 `startActivity`。可行形态至少有：

- (i) 把闹钟的**操作** PendingIntent 从 `getBroadcast` 改成 `getActivity`（到点由 AlarmManager 直接派发 Activity）；
- (ii) 用 `AlarmClockInfo` 的 `showIntent` 路径（系统在状态栏闹钟图标上发它）；
- (iii) 若走 (i)/(ii)，targetSdk ≥ 34 时**发送方需显式 opt-in**
  （`ActivityOptions.setPendingIntentBackgroundActivityStartMode()`），否则默认不放行。

| 利 | 弊 / 不确定 |
|---|---|
| 若成立，就是**零权限成本**地拿到界面 —— 不需要用户去开任何开关 | **缺少文档级确证**：官方那条例外写的是「系统**发送**的 PendingIntent」，AlarmManager 自动派发算不算「系统发送」，官方没有直说 |
| 改的是排程层，不引入新权限、不新增政策风险 | 与现有「解冻器 + 响铃服务」的顺序耦合，改错会**打破 H-08 的修复**（响与亮的主从关系） |
| | 本项目刚因「凭印象下结论」栽过（D58 撤回两条无文档支持的归因）⇒ **必须先做一次受控探针再决定** |

**建议的探针（约 15 分钟，不改产品代码）**：在现网 APK 上，用 CDP 注入复用
`AlarmScheduler` 的排程接口发一个 `getActivity` 版操作 PendingIntent 的闹钟，
在**无通知权限 + 息屏**下投递，读 `dumpsys activity activities | grep AlarmActivity`。
计数 ≥1 即证明该例外在 AlarmManager 路径上成立。**← 这一条建议先做，因为它决定 Q3 的排序。**

#### B-2 引导用户开 `SYSTEM_ALERT_WINDOW`（「显示在其他应用上层」）

**做什么**：清单里**早已声明**该权限、自检面板与设置页**也已有入口**
（`openOverlaySettings`），但**缺少「为什么需要」的说明与首用引导**，用户基本不会主动去开。

| 利 | 弊 |
|---|---|
| **官方清单里对第三方最明确可达的一条**（有文档依据，不像 B-1 要探针） | 要用户手动去设置里开，**转化率不确定** |
| 开了之后**一箭双雕**：既是 `startActivity` 的 BAL 豁免，也能直接画全屏覆盖层 | `SYSTEM_ALERT_WINDOW` 属敏感权限，商店可能要求说明用途 |
| 实现成本最低（入口都在，缺的只是「说清楚」） | **反面参照**：AOSP DeskClock **刻意不用**该权限（它的依据是「闹钟本该只需精确闹钟权限 + 通知」）|

#### B-3 补「不用界面也能停下来」的兜底停止入口

**做什么**：让「停止响铃」不只挂在界面按钮上。需要先确定**哪条路真的可用**：

| 具体做法 | 判断 |
|---|---|
| 响铃期间**动态注册 `ACTION_SCREEN_OFF`**（用户按电源键熄屏 = 我已注意到，停） | ⚠️ **有可行性**：动态注册合法、零权限；但「按电源键熄屏→停铃」是否是可接受的语义需产品判断 |
| **音量键**截获 | ❌ 需要窗口焦点或无障碍服务，**无可用 API** —— 不建议 |
| **电源键**直接截获 | ❌ 同样无可用 API；能做的只有上面那条「熄屏即视为已注意」 |
| 响铃期间**动态注册 `ACTION_USER_PRESENT`**（用户解锁完成 → 停下来并尝试亮出界面） | ⚠️ 逻辑上成立，但用户在无通知权限时**根本不知道有这个闹钟**，可能永远不解锁 |

| 利 | 弊 |
|---|---|
| **与 A-1 互补**：A-1 保证「一定会停」，B-3 让「想马上停的人能停」 | 语义要想清楚（「熄屏=确认」是不是把「关屏幕」误当成「已处理」） |
| 不引入任何权限 | 单靠它**解决不了「看不见」** —— 它只解决「停下来」 |

#### B-4（明确不建议）响铃期间「持续重试」拉起界面

原本作为候选 (b) 提出。**不建议作为主方案**：BAL 的判定**不是偶发失败，而是当前上下文的确定性属性**，
重试**不会产生任何新的例外条件** —— 本机实测在响铃前台服务**已经运行**的情况下仍为 0 可见（§1.2）。
把它当主方案，等于用一个「大概率永远不成功」的循环去掩盖真实缺口。
（成本很低，可作为附带动作保留；但**不应据此认为缺口已闭合**。）

## 4. 推荐组合（若你同意上述建议）

```
第一层（立即、低风险、把最坏后果消灭）
  A-1 自动静音上限        ← 消灭「响 6h 停不掉」
  A-2 排程时强引导通知权限 ← 在能挽回的时刻说
  Q5  改掉错误注释（1 行）

第二层（先验证，再决定）
  B-1 探针：系统 PendingIntent 能否拉起界面（不改产品代码，约 15 分钟）
        ├─ 成立 → 落地，界面这一格在无权限下也能到达
        └─ 不成立 → 转 B-2 引导 SYSTEM_ALERT_WINDOW
  Q6  全屏意图文案单独一轮（上架门禁）
```

## 6. 与基线的关系

**本提案预期不改动冻结基线**（与 D58–D61、D64–D67 同理）：它只决定
「闹钟档在降级态下的行为与引导方式」，不改 PRD 的档位路由、动作集与产品语义。
若 Q1 选 (a)（引入自动静音，等于给「响到确认为止」加时限），
**则该条可能需要一次基线级确认** —— 届时另立 CP 评估，不在本提案内自行推进。
