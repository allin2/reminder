## D34 · 提交隔离边界：取快照必须排在前一笔的成败（含回滚）之后

| # | 决议 | 依据 |
|---|---|---|
| **D34** | 所有持久化提交过一个**FIFO 闸门**，同一时刻只有一笔提交在跑；**快照在轮到自己时才生成**（不是请求时）。<br>动作的「写快照」与「失败回滚」必须**不可分割地占住闸门**（`commitActionOnce`）：失败时先在闸门内回滚完毕，才允许下一笔取快照。<br>闸门只改变**提交的先后与快照时刻**，不丢任何一次保存请求。 | I1：动作是「先改共享 state、再提交」的。提交未定成败期间用户完成另一个事项，那次保存若**立刻**取快照，就会把前一笔**尚未确定成败**的状态（ACK、派生出来的下一期、`alarmEventLog`）一起克隆进去。等前一笔失败、内存回滚之后，后一笔快照早已定型 —— 它成功落库就把这笔本该失败的动作**重新写回数据库**，重启后 ACK 与下一期重新出现，事件还被标成「已处理」。<br>用户看到的是「A 已回滚」，磁盘与重启后却是「A 已确认」，直接违反 V0.2 §19「看到的就是保存的」。<br>复核也点明：**串行化已经生成的快照修不了这个**，因为问题出在快照生成时刻，而不是写入顺序。 |

**实现位置**：`app-core.js` → `commitChain` / `runCommit()` / `writeSnapshot()` / `saveAsync()` / `commitActionOnce()` /
`performAlarmAction()`（`commitAttempted` 区分「同步体抛错」与「提交失败」两种回滚时机）。

> **第六轮补充（J1）**：本条的隔离只覆盖了「写快照 + 回滚」。动作的状态变更仍在**进入队列之前**发生，
> 于是**先排队**的普通保存出队取快照时会读到**后到**的动作 —— 反方向的同一个漏洞。
> 隔离边界已扩展到「校验 + 变更 + 派生 + 台账 + 提交 + 回滚」整体，见
> `review-round6-fixes-2026-09-17.md` 的 D35。本条其余内容保持第五轮当时的判断。

**为什么不给闸门设超时**：`storage.save` 用的是同一 object store 上的 `readwrite` 事务，
IndexedDB 本来就会把并发写按创建顺序串行化。所以闸门**没有新增延迟**，只是把既有的串行关系
显式搬到 JS 侧，从而消掉「快照生成时刻」的竞态；不存在「闸门卡住而存储其实空闲」的情形。

**闸门的副作用（已在测试基建中显式处理）**：启动期的 `save()` 是发后即忘的，它们会先占住闸门。
调用方的第一笔提交因此排在它们之后 —— 真机上这些写事务毫秒级完成，无影响；
但测试若同时扣住提交就会互相等死，所以回归 harness 提供 `boot()`
（启动 + 排空启动期写事务），让每个场景都从**空闲的闸门**开始。

## 本轮同时更正的判断（更正而非新增裁决）

1. **D33 里关于并发提交的论据不成立**（已在该文档原位加更正说明）。
   原文：「IndexedDB 事务按创建顺序串行，`saveAsync` 的调用顺序就是快照先后，所以最后落地的一定是最新的那份」。
   该推理只对「两笔都成功」有效；**前失败、后成功**时后一笔的快照仍是脏的。
   正确结论：必须让取快照排在前一笔的成败之后（即 D34），而不是只依赖写入顺序。
2. **H1 的验收表述随之收紧**：提交期间发起的普通保存，「不丢」的准确含义是
   **排进闸门、在前一笔定成败之后按当时的状态取快照并落库**，而不是「立刻发起一次独立的写事务」。
   回归断言已按此改写（先断言「此刻还没取快照」，再断言「最终落库且重启一致」）。
