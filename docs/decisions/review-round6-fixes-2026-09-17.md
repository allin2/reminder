第五轮的闸门挡住了「后到的动作污染先到的保存」，但动作的状态变更**仍在进入队列之前**发生 ——
于是**先排队**的普通保存出队取快照时，会读到**后到**的动作。这一轮把隔离边界补齐。

## D35 · 隔离边界必须同时覆盖「业务变更」与「提交」

| # | 决议 | 依据 |
|---|---|---|
| **D35** | 闹钟动作的**校验 + 状态变更 + 周期派生 + 事件台账 + 提交 + 失败回滚**整体作为一个**闸门任务**（`performAlarmAction` → `runCommit(applyAlarmAction)`）。<br>进入闸门之前**不得**对共享 state 做任何改动。 | J1：D34 只把「写快照 + 回滚」放进闸门，动作却是在入队**之前**就改好了共享 state。队列里已经排着的普通保存（S1）出队取快照时读到这笔**尚未提交**的 ACK —— 它成功落库就把这笔动作提前写进数据库；之后 ACK 自己的提交失败、内存回滚，也撤不回那一笔。<br>实测：前两笔成功、动作那笔失败后，内存 `A=due/items=2/seen=false`，磁盘与重启 `A=acknowledged/items=3/seen=true` —— 重启后 ACK 与下一期重新出现，事件还被标成「已处理」，违反 V0.2 §19「看到的就是保存的」。<br>复核意见原话：隔离必须覆盖业务变更与提交，不能只覆盖写快照与回滚。 |

**为什么必须两边都覆盖**（四轮迭代才收敛，值得记下来）：
- 只覆盖「提交」→ **I1**：后到的动作污染先到的保存（快照生成时刻晚于动作变更）；
- 只覆盖「写快照 + 回滚」→ **J1**：先到的保存污染后到的动作（快照生成时刻早于动作提交）；
- 只有把**校验、变更、派生、台账、提交、回滚**放进同一个串行边界，两个方向才同时关闭。

**实现位置**：`app-core.js` → `performAlarmAction()`（只做入队）／`applyAlarmAction()`（全部业务逻辑，
在闸门任务内执行）／`runCommit()`。拒绝路径保持不变：任务失败时**在闸门内**回滚完毕后让 Promise 拒绝，
原生队列据此不确认删除事件（绝不能把拒绝吞成成功）。

> **第七轮补充（K1）**：动作整笔进闸门解决了「谁看到未定成败的改动」，但**回滚本身**仍可能只撤掉一半 ——
> 派生实例被撤掉、动作写下的关联状态却留着，而用户随后的「完成本期」已经依赖过那个派生实例。
> 回滚已改为**逐字段**撤销并**重放**被破坏的顺延意图，见 `review-round7-fixes-2026-09-17.md` 的 D36。
> 本条其余内容保持第六轮当时的判断。

**代价（已知并接受）**：动作的界面效果（toast / 重渲染）随之推迟到轮到它执行时。
闸门在正常情况下一拍即空（同一 object store 的 `readwrite` 本来就要串行），
所以实际延迟是一次 microtask 到几毫秒；只有在前一笔写事务长时间未完成时才会更久，
而那种情况下底层存储本身也没有完成，属于既有约束而非新引入。

**仍未覆盖**：`handleNativeNotificationAction`（通知栏动作）同样是「先改变共享 state、再提交」，
但它**没有回滚**，所以不会产生「失败动作被复活」的反转；它的变更被更早的快照顺带写入时，
内存与磁盘是一致的（变更本身成立）。本轮不为它加闸门，留作独立事项。

## 本轮同时收紧的两条验收表述

1. **J1 的新增验收**（已落地为回归）：
   队列非空时「普通保存 → B 完成 → A 周期 ACK」，前两笔成功、A 那笔失败 →
   重载后必须 `A=due`、无下一期、无 A 的已处理标记、`B=archived`。
   另外断言**动作的状态变更必须等轮到它才生效**（`a.status === "due"` 直到它出队）——
   这条是 J1 与 I1 的分界点。
2. **「不丢后续操作」的准确含义**（延续第五轮的收紧）：普通用户操作的变更可以立即生效，
   但它的**快照**必须在它自己出队时生成；只要它没有回滚语义，就不存在「把失败动作写回去」的风险。

1. **全量入口**：`npm test` → unit 29 / native 103 / smoke 161 / regressions **88**，共 **381 项全部通过**；
   `git diff --check` 通过。
2. **区分度验证**：
   - 把 D30–D35 的修复**全部**按语义逐条回退 → 同一份回归**失败 38 项**。
   - **只回退 J1**（把动作的状态变更挪回队列之前，其余全部保留）→ **失败 32 项**，
     其中 J1 专项 8 条逐条对应复核探针的症状：
     `J1 动作的状态变更必须等轮到它才生效 — a=acknowledged`、
     `J1 磁盘：较早的普通保存不得把 A 的 ACK 提前写进去 — disk A=acknowledged`、
     `J1 磁盘：不得残留派生出来的下一期 — items=3`、
     `J1 磁盘：不得留下该事件的已处理标记 — {"evt-j1":…}`、
     `J1 重启后：A 仍是待处理且无派生残留 — {A:acknowledged, B:archived, <下一期>:waiting}`。
     （该回退手法会让动作被重复应用，因而连带若干无关断言失败；J1 专项本身的失败原因是精确的。）
3. **回归 harness 本轮增强**：`releaseCommits(n, mode)` —— 按创建顺序**逐笔放行并逐笔指定成败**，
   从而精确复现复核探针的「S0 成功 → S1 成功 → S2 失败」三步，而不是一起放行的近似。
