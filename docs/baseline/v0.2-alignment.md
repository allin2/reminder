### 1.1 容易误读：基线里的「可选」到底指什么

**基线里没有「用户选择默认通知方式」这个设置项。** 逐条查证：

| 位置 | 原文要点 | 实际含义 |
|---|---|---|
| §8 | 普通 / 重要 / 关键三档；关键「**用户显式开启**…在系统/权限允许时可使用闹钟级或更强提醒」 | **逐条**的提醒强度选择——这是基线里唯一真正的"选方式"，且**按条不按全局** |
| §5.1 | `importance`（NORMAL / IMPORTANT / CRITICAL） | 档位是**事项的属性**，不是全局设置 |
| §23 D-02 | 「移动 App 为最终主体；**主动推送可关闭**」 | 全局唯一明确的"可关"——是**开关**，不是选型 |
| §9.3 | Review 未响应「按**用户可配置**的间隔与次数有限补提醒」 | 可配置的是**补提醒参数** |
| §15 | 「普通事项可被**用户配置**的睡眠/会议/勿扰规则轻量过滤」 | 可配置的是**勿扰规则** |
| §17 标题 / §10.1 | 「MVP 默认规则（**可参数化**）」／「具体数值可在**实现阶段参数化**」 | 参数化＝**实现层常量**可调，不是给用户的界面选项 |

**结论**：用户的"选"发生在**逐条档位**上；全局层面只有"把推送整个关掉"。
所以「关键可用闹钟级」是一条**逐条可选**的能力——而代码目前还没把它接上，这正是 D9 要落地的。

> 全局「默认提醒方式」这个诉求已作为变更提案登记：见
> [`change-proposals.md`](./change-proposals.md) 的 **CP-001**
> （含与 D-04 / §8 / §17 的冲突评估与四个备选方案）。

**最重的一条**：V0.2 §5 + §22 要求**正交状态建模**（`attention_status` / `review_status` /
`completion_status` / `deadline_status`），而现状是**单一 `status` 枚举**把注意力与完成度混在一起。
这会是一次 schema 5 迁移，也是 P0 里影响面最大的一项。

### X1 ⚠️ 待整理入口：常驻弱入口 vs 只在窗口内

| | 内容 |
|---|---|
| **V0.2 §12** | 「待整理 ｜ 弱入口"待整理 · N"，**仅在 Review Window 或用户主动进入时提高存在感**。」 |
| **我们的 D6/D21** | 入口只在窗口 ∪ 宽限期内出现；不加窗口外入口，找回靠搜索 |

差异在于「**常驻但弱**」与「**不出现**」。V0.2 的写法意味着入口一直在，只是平时不显眼、窗口内变显眼。

➡️ **倾向 V0.2**：把入口改成常驻的低对比度一行（不带强调色、不带数字徽标），窗口内才提升显著性。
理由：V0.2 §12 同时要求「或用户主动进入时」提高存在感——若入口根本不出现，"主动进入"就没有落点，
只剩搜索一条路。而我们当初否掉常驻入口的理由（"白天持续提醒一笔未清的账"）可以用**降低显著性**
解决，不必用**隐藏**解决。

### X2 ⚠️ Fallback Trigger：下一个 Review Window vs now + 7 天

| | 内容 |
|---|---|
| **V0.2 §6.1** | 无法识别时间 → 「使用 Fallback Trigger，并进入 NEEDS_REVIEW。**默认 Fallback 为"下一个 Review Window"**；若未设置 Review Window，则使用系统默认次日晚间。」；§17 同 |
| **我们的 D17** | 兜底 `now + 7 天`，不进 `due`、不发提醒，到点只再推一次整理 |

两个差异：**兜底值**（下一个窗口 vs 7 天后）和**到点行为**。

➡️ **倾向 V0.2 的兜底值 + 我们的 D17 语义**，即：`trigger_at` 兜底为**下一个 Review Window**，
但仍**不进入「需要注意」**，到点只推一次整理。理由：7 天是我当时拍的默认值，V0.2 给的更聪明——
它让兜底时间与用户的整理节奏对齐，用户在整理时自然会看到它。

**⚠️ 联动风险**：V0.2 §9.2 允许「Review 功能可完全关闭」。一旦关闭，就没有"下一个 Review Window"，
按 D17 的"不发提醒"语义这些记录会被**永远搁浅**。V0.2 §9.2 同时要求「关闭后 NEEDS_REVIEW 数据仍保存，
**已有 Trigger 仍正常工作**」——所以 Review 关闭时，这一类记录必须退回**次日晚间**兜底（V0.2 §6.1 已给）
并正常进入提醒流程。这条要一起定。

### X3 ⚠️ Review 补提醒参数：60 分钟 × 2 次 vs 45 分钟 × 1 次

| | 内容 |
|---|---|
| **V0.2 §17** | 「Review 补提醒 ｜ 建议默认 **60 分钟间隔，补提醒 2 次（当天最多 3 次）**，最终滚入下一窗口。」 |
| **现状** | `settings.review.followupMs = 45 * 60 * 1000`、`maxFollowups = 1`（当天最多 2 次） |

➡️ **倾向 V0.2**：改成 60 分钟 / 2 次。这是纯参数，没有理由对抗基线。
（注意 V0.2 的"最终滚入下一窗口"与现状的 `skippedUntil` 语义基本一致，保留。）

### X4 ⚠️ 低置信度是否保留"极简选择"

| | 内容 |
|---|---|
| **V0.2 §6.1** | 低置信度 → 「保存成功，同时标记 NEEDS_REVIEW；**仅在必要时给极简选择**。」 |
| **我们的 D15** | 完全不弹确认框，一律收下、延后澄清（并据此删掉 `#sheetLowConf`） |

V0.2 没有把即时选择删干净，留了"仅在必要时"的口子。

➡️ **倾向 V0.2 的保守读法**：主路径不弹（保留 D15），但**保留"必要时"的判定与 UI 能力**，
不把 `#sheetLowConf` 当死代码删掉——否则违反 §22「不自行优化产品逻辑」。
建议在规格里写明什么算"必要"（初步建议：解析结果明显冲突、或解析出的时间已过去），
但这需要你定。

### X5 ⚠️ 归档重新打开是否产生新提醒

| | 内容 |
|---|---|
| **V0.2 §19 AC-18** | 「归档事项可重新打开为未完成，**但不自动产生新提醒**。」 |
| **现状** | `restoreItem()` 把状态改回 `waiting`，并把 `triggerAt` 设为 **now + 1 小时** → 会产生新提醒 |

这是现状与基线的**直接冲突**，且不在我们 D1–D21 的覆盖范围内（我们没问到它）。

➡️ **倾向 V0.2**：重开为未完成但**不设 triggerAt**，落到"无时间"从而进入 NEEDS_REVIEW / Future。
若用户要提醒，由他自己设时间。理由：AC-18 的意图明确是"恢复 ≠ 重新安排"。
**但**要留意：`waiting` 但没有 `triggerAt` 的事项在现状下不会出现在任何首页区块，只会在「未来」页——
这正是 V0.1 §18 允许的。**这条我建议你明确一下：重开后应该出现在哪里？**

### X6 ⚠️ 「今天已完成 N 件」是否算注意力噪声

| | 内容 |
|---|---|
| **V0.2 §13** | 「历史不主动制造"年度总结/**完成数**"等注意力噪声。」 |
| **我们的 D8** | 空态里补一句「今天已完成 N 件」 |

V0.2 那句针对的是"历史/年度"层面的噪声，而 D8 说的是**当天空态**的一行。字面上有张力。

➡️ **倾向保留 D8，但降级为纯文字**：不带数字徽标、不可点击、不与「需要注意」抢视觉。
如果你认为连这一句也算噪声，就退成 V0.1 的「此刻很安静」。

### X7 ⚠️ 冷启动是否直接进入输入页

| | 内容 |
|---|---|
| **V0.2 §6** | 「**打开 App 默认直接进入输入页**。」 |
| **现状** | 冷启动进首页；只有分享参数进来时才 `openCapture()` |

这条 V0.2 与「首页 = 需要注意」的模型有张力：如果每次冷启动都是输入页，用户就看不到
「现在需要注意」。

➡️ **倾向澄清后再定**。我的读法是这句在说「**Capture 是主入口**」（针对桌面快捷方式/分享进来时直达输入页），
而不是「冷启动跳过首页」。建议按「冷启动进首页；快捷入口与分享直达输入页」实现，并把 V0.2 那句
标注为待澄清。**这条需要你确认**，因为直接影响首屏。

## 4. 全新需求（V0.2 有、我们完全没有）

### 4.1 P0 · 数据与状态模型

| # | 需求 | V0.2 出处 | 影响面 |
|---|---|---|---|
| G01 | **正交状态建模**：`attention_status` / `review_status` / `completion_status` / `deadline_status` 四个独立维度 | §5、§22 | **schema 5 迁移**；现状单一 `status` 把注意力与完成度混在一起（`archived` 同时表达"已完成"和"已归档"） |
| G02 | `original_capture`：保留原始录入文本，用户修改后可回溯，前台默认隐藏 | §5.1、§13 | 需新增字段 + 详情页回溯入口 |
| G03 | `time_source`（PARSED / USER / FALLBACK） | §5.1 | 新增字段；解析、手工改期、兜底三条路径都要写入 |
| G04 | `version` + **旧通知动作版本校验**：旧通知不得覆盖新状态 | §5.1、§14、§22 | 现状 `scheduleKey` 只能判断"这条通知是否还是想要的"，无法拒绝旧动作回写 |
| G05 | `updated_at` | §5.1 | 新增字段；与 G04 配套 |
| G20 | `deadline_status`：NONE / PENDING / PROTECTED / **PASSED** | §5、§10 | Deadline 到达未完成要进入风险状态，允许完成/重排/保留，**不无限轰炸** |

> ⚠️ **G01 是 P0 里最重的**。V0.2 §22 明写「业务状态必须正交建模，不得使用组合爆炸式枚举」，
> 而现状之所以出现 `completed` 幽灵状态（见 `docs/product-logic.md` 的 I4），根因就是维度混用。
> 建议把它排在**所有其他 P0 之前**，因为它决定后续所有字段与测试的形态。

### 4.2 P0 · 可靠性与自愈（V0.2 §14 整章）

| # | 需求 | 现状差距 |
|---|---|---|
| G06 | **删除支持短时 Undo** | `deleteItem()` 确认后直接移除，无撤销 |
| G07 | **编辑时间三步顺序**：取消旧调度 → 保存 → 建新调度 | 现状靠 `queueNativeReminderSync()` 的 80ms 去抖 + 全量对账兜底，未显式保证顺序 |
| G08 | **时区/系统时间变化**：已错过且未 ACK 的事项必须进入「需要 Attention」，**不得静默跳过** | 有 `scheduleBasis` 重算，但没有"已错过必须浮上来"的显式规则 |

## 6. 已被 V0.2 确认、无需改动的现状

**首页信息架构**（§12）：两视觉 + 弱化的待整理入口 + Future 默认隐藏 + Badge 只算待确认数 —— 除 X1 外全中。
**ACK 语义**（§8.1）：现状只把「我知道了 / 稍后 / 完成」当作显式动作，不根据解锁或打开 App 推测 —— 全中。
**Capture 不失败**（INV-01 / §6）：现状任何输入都保存 —— 全中。
**数据库为事实来源、调度可重建**（INV-09 / §22）：现状正是投影 + 全量对账 —— 全中。
**离线可用**（§14 / AC-15）：IndexedDB + Service Worker，核心链路不依赖网络 —— 全中。
**不做优先级判断、不建设项目关系**（§1.3 / D-01 / D-09）：现状 priority 只由用户主动标，无自动排序 —— 全中。
**周期两种模式**（§11）：calendar / ack 两种起算 —— 全中。
**重复捕获不自动合并**（§13 / AC-16）：现状只提示"可能已有类似提醒" —— 全中。
**Archive 不主动浮现**（§12）：现状归档只在「未来 → 已归档」分段里 —— 全中。
