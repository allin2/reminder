## A-01 · 全局默认提醒方式 + 标记项强制闹钟

| | |
|---|---|
| **批准日期** | 2026-09-16 |
| **来源** | 变更提案 [CP-001](./change-proposals.md) |
| **状态** | 已批准，**待实现** |
| **实现规格** | [`../compose/spec/delivery-mode.md`](../compose/spec/delivery-mode.md) |

### 生效语义

| # | 规则 |
|---|---|
| **R1** | 新增全局设置 `defaultDeliveryMode` ∈ { 闹钟提醒, 系统通知 }，**随时可改** |
| **R2** | **未标记**的事项 → 按 `defaultDeliveryMode` 提醒 |
| **R3** | **有标记**的事项（☆重要 · 🚨关键）→ **一定是闹钟提醒** |
| **R4** | 其余原有逻辑不变（ACK ≠ 完成、Future 默认隐藏、三档追踪频率、Deadline Protection） |

### 条款级修订

| 基线条款 | 原文 | 修订后 |
|---|---|---|
| **§23 D-04** | 「普通事项有限追踪；重要事项持续更强追踪；关键事项可闹钟级。」 | 「普通事项有限追踪，**投递方式取全局默认**；重要事项持续更强追踪，**投递方式固定为闹钟级**；关键事项采用系统允许的最强可用机制。」 |
| **§8 重要 行** | 「A+B：重复提醒 + 提高通知显著性；持续追踪强于普通事项。」 | **追加**「**投递方式固定为闹钟级**」 |
| **§8 关键 行** | 「用户显式开启；在系统/权限允许时可使用闹钟级或更强提醒。不得偷偷降级而不告知。」 | **不改**——仍然成立；但"闹钟级"从此**不再是关键档专属** |
| **§17 关键事项 行** | 「仅显式开启；采用系统允许的最强可用机制。」 | **不改**——「仅显式开启」约束的是**档位选择**，不是投递方式 |
| **§8 / §5.1 档位语义** | 档位 = 追踪频率 + 通知显著性 | **追加**：档位与投递方式是**两条正交轴**。档位仍决定频率与显著性；投递方式由「有标记 → 闹钟 / 无标记 → 全局默认」决定 |
| **§17 相同时间多事项** | 「普通事项可聚合；重要/关键可单独显示。」 | **原文保留，但记录已知冲突**：若 `defaultDeliveryMode = 闹钟`，普通事项的首次提醒是全屏，**无法聚合**。聚合仅对走通知的提醒成立 |

### 十条不变量核验

| 不变量 | 影响 |
|---|---|
| INV-01 Capture 不失败 | 不受影响 |
| INV-02 Trigger 不被 Review 阻断 | 不受影响 |
| INV-03 仅显式 ACK 才算看到 | 不受影响（全屏的「关闭」不写 ACK，见 D12） |
| INV-04 ACK ≠ Complete | 不受影响 |
| INV-05 Deadline Protection 不被静默覆盖 | 不受影响 |
| INV-06 丧失提醒能力必须告知 | **受益**——本修订让"我愿意／不愿意被强提醒"成为可表达的用户意愿 |
| INV-07 未来事项默认不占首页 | 不受影响 |
| INV-08 Review 只提高信息质量 | 不受影响 |
| INV-09 数据库是事实来源、调度可重建 | **需注意**：快照模式下 `delivery_mode` 必须入库并参与对账重建，否则重建后投递方式会漂移 |
| INV-10 自动化宁可保守 | **受冲击**——全屏闹钟变默认体验会放大"被打断"的代价，用户可能整体降级。**已作为知情代价接受** |

### 知情代价（2026-09-16 已接受）

1. **「关键」档贬值**——人人都全屏响，等于人人都被忽略。
2. **§17 的聚合行为对普通事项失效**——全屏界面一次只能显示一条；三条普通事项同时到期即连响三次。
3. **用户可能整体降级**——会议／驾驶／通话中的抢屏会让人把默认改回"系统通知"，
   连同真正标记关键的事项一起被降级。这正是 INV-10 要防的反面。

> 这三条**不阻止本修订**，但必须随基线一起被读到，而不是等实现时才暴露。
