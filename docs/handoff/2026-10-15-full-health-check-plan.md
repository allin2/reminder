## 0. 给执行 Agent 的总规则（必读）

1. **只体检，不修代码。** 除非任务书里明确写了「允许修复」，否则一律只记录。发现可以一行修好的问题，写出建议改法和验证方式即可。
2. **结论必须带证据。** 每条发现都要有以下至少一种：`文件:行号`、命令及其输出、截图、`adb`/logcat 片段、测试断言名。**没有证据的推测必须标「推测」**，不得写成结论（本项目吃过「凭记忆报缺口」的亏，见 [release-gates](../decisions/release-gates-2026-09-19.md) 开头的更正）。
3. **对照设计判定，不按个人偏好判定。** 「不符合预期」必须指向基线里的具体条款（INV-xx / AC-xx / §x / D-xx）。产品刻意的取舍（第 1.3 节）不算缺陷。
4. **区分「读不到」和「没有」。** 证据通道读失败、权限未知、桥未就绪时，结论是「未知」，不是「失败」（基线红线，见 `lib/app-notices.js` 的 `homeNoticeVerdict` 注释）。
5. **先复核已知问题，再找新问题。** 第 4 节列出的已知问题请先逐条确认「仍存在 / 已修复 / 无法复现」，避免重复上报。
6. **真机操作边界**:
   - 测试机是用户本人的手机。**解锁、USB 安装确认、系统设置开关**需要用户本人在手机上操作，Agent 不得尝试输入锁屏密码；
   - 允许：`adb install -r`（保留数据）、`am force-stop`、`dumpsys`、`logcat`、WebView 远程调试；
   - 需要先在聊天里征得用户同意：`adb reboot`、`pm clear`（清数据）、卸载、修改系统时间/时区、撤销权限。
7. **输出**: 每条检查线交一份报告，放在 `docs/reviews/health-<线编号>-<YYYY-MM-DD>.md`，格式见第 5 节。

## 1. 产品设计基线摘要（判定标准）

### 1.1 产品承诺

> 让用户把未来的事交出去后**可以放心忘记**；到点时**可靠地**重新拿回注意力，并且**明确知道用户是否真的看到**。

### 1.2 十条不变量（任何实现不得违反，违反即 P0/P1）

| 编号 | 不变量 | 体检时重点看什么 |
|---|---|---|
| INV-01 | 捕获不能因信息不完整而失败 | 乱码、空时间、超长、emoji、纯模糊词都必须能保存 |
| INV-02 | 已有的提醒不能被「待整理」状态阻断 | 带具体时间且待整理的事项，到点必须照常提醒 |
| INV-03 | 只有显式操作才算「用户已看到」 | 解锁、打开 App、划掉通知、全屏「关闭」都**不得**写 ACK |
| INV-04 | 「我知道了」不等于完成 | ACK 后仍在「已看到未完成」，可再次被截止保护唤醒 |
| INV-05 | 截止保护不能被普通状态静默覆盖 | ACK / 稍后 / 待整理之后，p24 与 p2 两个保护点仍然生效 |
| INV-06 | 失去提醒能力必须明确告知 | 通知权限、精确闹钟、原生桥、对账失败、网页版限制 |
| INV-07 | 未来事项默认不占首页 | 首页没有「即将到来」长列表 |
| INV-08 | 待整理只提高信息质量，不升级为任务管理 | 不出现项目/子任务/看板类功能 |
| INV-09 | 数据库是事实来源，系统闹钟是可重建的执行层 | 清掉系统排程后能通过对账重建；不存在幽灵闹钟 |
| INV-10 | 自动化宁可保守，不得因「智能」漏提醒 | 解析/去重/降级逻辑出错时必须偏向「多提醒一次」而不是「少提醒」 |

### 1.3 刻意的产品取舍（不是缺陷，不要上报）

- 未来事项默认隐藏，首页没有「即将到来」列表；
- 不替用户判断优先级，只有用户主动标记「重要/关键」；
- 不做项目管理、番茄钟、效率统计、打卡；
- 「我知道了 ≠ 完成」、完成可撤销、新建 8 秒可撤销；
- 全屏闹钟的「关闭」只止响、不表态（D12）；
- 关机期间错过的闹钟**不集中补响**（防群响），而是记入漏响台账、告知用户。

### 1.4 关键规则速查

| 规则 | 值 / 位置 |
|---|---|
| 重提醒策略（唯一来源） | `lib/reminder.js` 的 `REALERT`：普通 1 次；重要 4 次 / 30 分钟；关键 8 次 / 15 分钟（次数含首响） |
| 投递方式（A-01） | 有标记（重要/关键）一律闹钟；无标记按全局默认 |
| 截止保护 | p24（截止前 24 小时）+ p2（截止前 2 小时），逾期后 24 小时宽限 |
| 补投窗口 | 错过的触发点 24 小时内补一条普通通知（不抢全屏） |
| 台账状态 | `scheduled` / `delivered` / `cancelled` / `suppressed` / `lost`（2026-10-15 新增） |
| 闹钟渠道 | `attention-alarm-v5`：无声、无振动（D59，声音由 `AlarmRingService` 播放） |
| 单次排程上限 | 400 条（`MAX_SCHEDULED`） |

## 3. 检查线（每条可派给一个 Agent）

## 5. 报告格式（每条检查线一份）

```markdown
# 体检报告 · T<n> <检查线名称>

- 执行人 / 日期 / 代码版本（HEAD + 未提交文件数）/ 设备与系统版本
- 覆盖率：计划 X 项，执行 Y 项，跳过 Z 项（逐条写跳过原因）

## 结论（3 句以内）

## 用例结果
| ID | 结果（✅ / ❌ / ⚠️ 部分 / ⏭ 跳过 / ❓ 未知） | 证据 | 备注 |

## 发现的问题（按严重度排序）
### <级别>-<序号> 一句话标题
- 违反条款：INV-xx / AC-xx / §x / D-xx
- 复现步骤（可被另一个人照着做）
- 期望 vs 实际
- 证据：文件:行号 / 命令输出 / 截图
- 影响面：哪些用户、多常见
- 建议修复（可选）与验证方式

## 已知问题复核（第 4 节逐条：仍存在 / 已修复 / 无法复现）
```

### 严重度定义

| 级别 | 定义 | 例子 |
|---|---|---|
| **P0** | 违反不变量，导致**漏提醒、重复打扰、数据丢失**，或系统失去提醒能力却**不告知** | 该响不响、响两次、删了还响、捕获失败 |
| **P1** | 核心路径体验明显受损，或可靠性降级但用户有感知 | 计数显示错误、页面错位、关键文案误导 |
| **P2** | 体验瑕疵、一致性、可维护性 | 文案、按钮尺寸、lint 告警 |

## 6. 建议的派工与顺序

| 批次 | 并行的检查线 | 说明 |
|---|---|---|
| 第 1 批（无需真机，可立即并行） | T1、T2、T3、T4、T6、T7、T9、T10 | 每条一个 Agent。T4 最需要深度，建议用最强模型 |
| 第 2 批（需要真机 + 用户在场） | T5、T8 的真机部分 | 同一时间只能有一个 Agent 操作测试机；先装新包（需用户解锁并确认安装），先做 HC-T5-0 |
| 汇总 | 1 个 Agent | 合并各线报告 → `docs/reviews/product-health-check-r3-<日期>.md`：去重、按严重度排序、对照第 4 节更新状态、给出修复顺序 |

**汇总报告的完成标准**: 每个 P0 都有可复现步骤和证据；第 4 节每一条都有最新状态；列出所有因「需要用户操作」而跳过的用例，方便用户集中安排一次真机时间。
