## 4. 实施顺序与完成条件

### 第一批：先建立测试与正确性边界

#### O1. 补生产组合启动测试，保留故障注入能力

范围：`test-smoke.js`、`test-regressions.js`；必要时新增一个职责单一的 harness/helper 或独立启动测试，并挂入 `npm test`。

- 从 `index.html` 解析实际外部脚本的**顺序**，在隔离 VM/browser context 中加载同一生产组合，确认预期导出与应用 ready；未知脚本、缺失文件或顺序错误要有明确失败。
- 保留现有 require 注入及平台故障 mock 用例。不要机械把 native 脚本再执行一遍，导致双实例、双监听或宿主 global 与沙箱 root 混用。
- 补一个可控 Android 桥场景：通过真实初始化和生命周期入口观察监听注册、一次排程、相同计划再对账不重排。明确监听返回同步句柄与 Promise 两种契约；若已有覆盖可引用并复用。
- 增加删掉 native 脚本/破坏顺序的反向对照，证明组合断言真的能抓缺失；不能只统计列表长度或判断导出变量存在。
- 新增运行模块才同步 index、SW、harness、打包复制链；不要为补测试无故修改运行脚本或升缓存版本。

完成条件：生产组合可启动、真实原生模块实际被调用、专项失败场景继续有效；基线数量变化可解释。

#### O2. 修通 deferNativeSync，消除无意义的反馈同步

范围：`app-core.js` 的 `save`、`saveAsync`、`writeSnapshot`、`syncNativeRemindersNow`、台账回写调用方。

- options 沿调用链传递到正确的 writeSnapshot 参数位置；队列仍然**轮到提交时才取快照**，不能在入队时提前冻结普通保存，也不能把 options 当 payload。
- 确认内部排程结果记账确实不再自动排下一轮。审查 deadline/reminder 台账写回的保存调用；区分“仅确认投影结果”与“改变后续计划的业务变更”，不要把所有事件保存一律禁用同步。
- 不吞掉同时发生的用户保存、版本变化、失败重试或旧轮补偿。保留 in-flight 串行、pending 和版本保护，不能通过简单时间窗丢请求。
- 在真实 app 编排链计数：同步请求、reconcile 执行、schedule/cancel 桥调用分别记录。不能只用直接调用 native.reconcile 的测试证明 app 层没有反馈循环。

完成条件：仅内部确认记账时不产生无谓后续对账；业务改变后最终计划正确；失败保留重试；不把“排程 API 调用成功”升级为送达成功。

#### O3. 修复链接协议和属性转义边界

范围：`app-core.js` 中本次确认的事项链接/ID 渲染及共用 actionButton；如已有安全工具则复用。

- 可点击的外部事项链接只接受解析后协议为 `http:` 或 `https:` 的绝对 URL。其他输入作为转义后的纯文本呈现，保留原始数据，不静默删除用户内容。
- 不用单纯 startsWith 或 escapeHtml 代替 URL 协议校验；覆盖大小写、首尾空白、控制字符、畸形 URL、javascript/data/file 和正常 HTTPS。
- 所有与该事项 ID 相关的 HTML 属性输出都按属性上下文转义。沿实际导入 normalizeItem → renderItemCard/actionButton 路径检查，不假定 ID 必由 uid 生成。
- 不顺带重编号既有 ID，不删除重复 ID。先保持既有匹配行为，重复 ID 数据治理另案。

完成条件：危险协议没有可点击执行入口；含引号 ID 不突破属性，正常链接与事项操作仍可用。通过真实 DOM/浏览器确认渲染边界，不仅查源码字符串。

### 第二批：减少重复计算与分配

#### O4. 台账、原生排程及证据匹配使用调用内索引

范围：`app-core.js` 的 applyDeadlineEvents、applyReminderEvents、applyNativeDeliveryEvidence；`lib/native-reminders.js` 的 reconcileAlarms。

- 把逐事件/逐事项的整表 find 改为每次调用内建立一次索引；对空台账的过滤可作最小优化，但不跳过应登记的新计划或应撤销的旧计划。
- 保持 `Array.find` 的首项匹配语义：重复 ID 不能因 `new Map(items.map(...))` 变成末项覆盖。不要引入需要跨所有修改入口维护的全局缓存。
- 保留旧轮次、delivered/suppressed/cancelled、截止阶段和 roundBase 语义，不借性能改动清除旧证据。
- 第一步可保留台账 JSON 比较。只有完整定义键集合、字段、缺省值与未知字段的等价语义后才替换；“去掉 stringify”不是必须完成项，避免同时改算法和数据判等。
- 度量不只记录 wall time：记录 n、事件数、目标数、find 比较次数、索引构建次数。总工作量按 n + 事件/台账规模增长；排序等其它工作单列。

完成条件：100/500/2000 事项，空台账和满台账均不出现逐目标整表扫描；原生 desired×items 查找消除；所有事件与持久化结果保持一致。

#### O5. 正常保存复用独立快照，少一次全量 parse

范围：`app-core.js` 的 writeSnapshot 及 committedAlarmItems 更新；默认不改 schema 或存储后端。

- 同一次序列化产生的独立快照在后端保存与已提交快照消费者之间复用，正常路径减少一次全量 parse；禁止把 state 活对象直接传给异步后端。
- 已提交快照只在权威提交成功后发布。失败不能提前更新 committedAlarmItems，不得让旧投递因未提交的新状态被误停。
- 保留 localStorage 镜像尽力写、IDB 权威、无 IDB 本地权威和 pending-replay 语义；不能为性能去掉镜像或回放，也不能把主键和镜像算作两个不同键。
- 对 memory 后端的对象别名明确处理，保证后续变更不污染已提交判定。若复用产生别名风险，保留必要隔离并如实报告，不能以少一次 parse 为由破坏事务。

完成条件：真实 writeSnapshot 路径有序列化计数对照；IDB 延迟/失败、镜像失败、无 IDB、IDB 打不开、恢复回放与重启读回均保持契约。

### 第三批：减少无用 DOM 工作

#### O6. 折叠内容按需生成，首页局部更新

范围：`app-core.js` 的 renderHome、renderItemCard、首页相关刷新调用；只有必要时局部改 `index.html`。

- “已看到未完成”折叠时只生成入口/数量，不生成隐藏卡片；展开后按当前状态生成，收起后释放不再需要的卡片 DOM。保持数量、排序、展开状态及动作行为。
- 首页无显示变化时避免替换卡片容器。优先使用局部容器内容/依赖比较或明确的视图模型，避免全状态 stringify 建签名本身复制热点。
- 签名/失效条件覆盖可见时间文案、跨分钟/跨日、提醒到点、勿扰边界、整理高亮窗口、权限/可靠性提示、项目/标签显示和展开状态；不得只依赖事项 rev。
- `promoteDue` 有业务副作用，不能藏在渲染短路后跳过。将业务推进与可跳过的 DOM 写入明确分开，避免 tick 与 renderHome 重复推进；保留必要的其它入口。
- 稳定 DOM 后检查焦点、滚动、按钮忙碌态及事件闭包是否仍引用最新事项；不能保留旧 card/action 回调而对已变更事项操作。
- 不引入虚拟列表库或前端框架；分页/虚拟化放入后续评估。

完成条件：1000 条 acknowledged 事项折叠时生成 0 张隐藏卡片；无显示变化的一拍不替换卡片节点；时间、数据或状态改变时及时更新。计数基准与真实浏览器交互都要有证据。

#### O7. 合并启动重复渲染

范围：`app-core.js` 的 init、handleQueryActions、applyShareParams、tick/render 的启动调用关系。

- 合并分支里的重复 render 与末尾 render/tick 的重复首页渲染，让加载、分享入口、查询参数路由确定后再执行必要的初始显示。
- 不靠删除首次 tick 延迟到期提醒 15 秒；不靠丢掉 handleQueryActions 或改变计时器安装时机减少计数。
- 保留干净首启无自动 seed、ready 信号、旧数据恢复、通知/深链、分享捕获、整理入口和后台桥异步初始化。

完成条件：默认空首页一次启动只做一次必要的首页 DOM 构建；到期事项立即处理。特殊路由若确有额外更新，按场景解释，不为满足“1 次”冻结 UI。

## 6. 性能与内存对照方法

- 优化前后使用同一个可复跑的合成数据生成器、固定 seed、相同 Node/browser 版本及操作。数据至少 100/500/2000 条，分开测 waiting、due、acknowledged、archived 分布，并包含有/无台账、较长备注。记录实际 JSON 字节数，不能只报事项数。
- 记录保存路径 JSON 调用次数、持久化写入次数/字节量、reconcile 请求/执行次数、桥 API 次数、生成卡片数与 DOM 写入数。计数用于证明机制消除，不以一次偶然耗时作为验收。
- 对时间测量先预热，再至少取 30 次同类操作，保存原始样本、median/p95；声明是否计入存储和异步桥等待。涉及时序正确性的测试使用可控时间，性能采样用真实计时，两者分开。
- 浏览器场景记录首次渲染、折叠/展开、空闲刷新、连续编辑/完成后的 DOM 节点与可用堆指标。区分驻留内存、瞬时分配和持续增长；强制 GC 后数字与正常运行数字不得混用。
- Android 数据若已获用户设备操作授权且环境可用，单列 app/WebView 进程内存及重复操作轨迹，绑定 WebView 版本和产物哈希；不凭桌面结果乘固定倍数推算，不因没有真机就编写“无感/省电”。
- 本轮无需预设缺乏基准支撑的“降低30%”目标。硬验收是 V01–V11 的行为与复杂度/DOM/JSON 计数；性能数据用于报告实测收益及未改善部分。
