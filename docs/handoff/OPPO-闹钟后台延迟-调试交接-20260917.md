日志 stage：requested → item → scheduled → received → environment → launchRequested / notifyReturned → created → audioState / audioStarted → resumed / focus / windowSample → userAction / effectsStopped / paused / stopped / destroyed。另有 scheduleFailed、notifyFailed、audioFailed、cancelled、replaced、duplicateIntent、autoClose。

## 6. 一次受控复现，抓住“打开之前”

### 6.1 启动持续日志

独立终端沿用上面的 ADB / SERIAL / RUN，**不要 logcat -c**：

```sh
"$ADB" -s "$SERIAL" logcat -v epoch -b main -b system -b crash > "$RUN/logcat.txt" 2>&1
```

实验结束 Ctrl-C 停止。不要只按当前 PID 过滤，进程可能死亡/重启；先保留本地原始文件，后按包名、UID、PID 时间段、AlarmManager、ActivityTaskManager、BroadcastQueue、BAL、Oplus/ColorOS 相关实际出现的 tag 检索。不预设厂商日志一定公开。

### 6.2 快照函数

在另一个终端定义；每次 phase 名唯一，避免覆盖：

```sh
snapshot() {
  local phase="$1"
  date '+%Y-%m-%dT%H:%M:%S%z' > "$RUN/$phase-host-time.txt"
  "$ADB" -s "$SERIAL" shell date '+%Y-%m-%dT%H:%M:%S%z' > "$RUN/$phase-device-time.txt"
  "$ADB" -s "$SERIAL" shell cat /proc/uptime > "$RUN/$phase-uptime.txt"
  "$ADB" -s "$SERIAL" shell dumpsys alarm > "$RUN/$phase-alarm.txt"
  "$ADB" -s "$SERIAL" shell pidof "$PKG" > "$RUN/$phase-pid.txt" 2>&1
  "$ADB" -s "$SERIAL" shell dumpsys activity processes > "$RUN/$phase-processes.txt"
  "$ADB" -s "$SERIAL" shell dumpsys activity broadcasts > "$RUN/$phase-broadcasts.txt"
  "$ADB" -s "$SERIAL" shell dumpsys window > "$RUN/$phase-window.txt"
}
```

1. 基线 `snapshot baseline`。
2. 用户正常表单新建独特标题（例如“USB调试-1730”）、关键、手选约 3–5 分钟后的时间；只建一条，不运行测试按钮，不设截止/重复。记录保存点击的时间、准确 triggerAt、itemId、rev、notify 开关、delivery_mode、isFallbackTrigger。
3. 保持前台直到取得 `snapshot after-save`，确认 dumpsys alarm 内本次 PendingIntent 存在，triggerTime 与计划一致，确实为 alarmClock / exact。别仅看 SharedPreferences。
4. 用户按 Home、锁屏；标记时间，`snapshot background`。本轮不滑掉最近任务、不 force-stop、不 kill；这些不是普通后台，须另做实验。
5. 计划前约 10–20 秒采 `snapshot before-due`。
6. 到点后约 10 秒、60 秒、120 秒分别采 `snapshot due-plus10` / `due-plus60` / `due-plus120`，**这段期间绝不打开 App、不点击通知、不调用 JS bridge、不刷新自检、不按“立即重排”**。注意若用户已目视看到闹钟，此轮成功事实独立记录。
7. 若持续没响，先保存 `snapshot before-open`。用主机/设备时钟标记用户点击图标的时间，再由用户打开 App，随后 `snapshot after-open`。查看广播究竟在打开前还是打开后进入 Receiver，是否有新的 scheduled/token。
8. 打开后先不 ACK/完成/改期，及时导出 trace；如铃声干扰，记录停止按钮的准确时间和动作再处理。

USB 充电、保持唤醒、调试连接都可能改变后台行为。记录插线状态与屏幕设置；先不修改。若 USB 下故障消失，只能写“带 USB 未复现”，后续再设计明确授权的断线/无线对照，不能把它判为修复。

## 8. 分支判定与修复方向

| 证据 | 可下的结论 | 下一步 |
|---|---|---|
| 保存后无本次系统闹钟，直到重新打开才出现 | 原生登记链可能延迟或漏执行 | 查保存 Promise、80ms debounce、初始化、桥调用失败、后台切换；做最小复现 |
| 保存后正确登记，后台期间被取消/替换 | 调度被撤销，不是单纯窗口问题 | 对齐全部 token、cancel reason、调用者、rev/状态变化；区别自然出队与取消 |
| 到点后仍在系统队列且被延后，前台后才投递 | 存在延迟事实，原因还需系统信息 | 检查实际 mode、权限/standby/厂商限制和队列 policy；不先改所有权限 |
| 系统显示已出队，但直到开 App 才有 Receiver 记录 | 出队不等于 Receiver 已执行 | 查进程拉起、广播派发/挂起/冻结/异常；确认时钟与日志完整性 |
| 打开后出现新 scheduled token，再收到广播 | 更像前台重排而非原计划正常投递 | 区分原 token 和新 token，追 onResume / reconcile |
| 广播准时收到，窗口/audio 后续失败 | 进入显示/播放器分支 | 查 trace 焦点、启动拒绝、audioFailed、通知 channel；需要时回到窗口调查 |
| 调用 ack 之前已被归档或状态变更 | 可能是应用业务链干扰 | 查动作队列、eventId、版本校验与用户动作来源，不能假定用户误操作 |

同一 ID 的重排会更新 PendingIntent extras，必须比较 token 而不是只看 id。只发生一次 9 秒迟到、且恰好用户打开，不能单独证明“永远等打开才触发”。应安排足够等待窗口和至少一个不提前打开的对照。

若证据不足，先增强一处缺失证据，再实验；不要同时更换 FSI、前台服务、AlarmManager API、权限、进程保活等多个变量。不要用永久前台服务或悬浮窗轮询掩盖未定位问题。
