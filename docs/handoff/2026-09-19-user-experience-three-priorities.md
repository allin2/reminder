# 安心收件箱：可信提醒、轻量录入、清楚处理的实施与验收方案

日期：2026-09-19。方案版本：1。

状态：实施交接方案，尚未实现、尚未验收。本次只新增本文件。

用户要求：根据产品评价与三个优先项形成实施方案，交由其他 agent 实现，再回到原任务由方案 agent 独立验收。本方案不自动派发任务、不创建后台监控。

## 1. 目标、实施依据与保护边界

用户可观察的成功条件：

1. 保存后，能区分「记录已保存」「提醒已安排」「能力受限」「结果暂不确定」。
2. 新用户无需阅读文档即可记录第一件事，并知道什么时候提醒；没有时间的记录不被拒绝，也不冒充已安排了事项提醒。
3. 用户能预测「我知道了 / 稍后提醒 / 完成」的后果，误操作有明确恢复路径，几天后仍找得到未完成事项。

本文件提供完整推荐规格。用户把「按本方案实现」交给实施 agent 后，包含下文的 Web UI、保存反馈、必要原生证据回流、有限撤销及验收工作，不再因它们是多步工作重复求批。仅转发文档供讨论不等于实施授权。新发现若需要改变本文明确保留的产品行为或操作个人设备设置，只处理相关歧义，不暂停独立工作。

## 4. P1：让用户知道提醒准备到了哪一步

### UX-T01 保存结果与排程结果分开

- 新建和编辑均覆盖：保存中有反馈、避免重复提交；权威持久化确认前不能显示「已保存」或清掉输入。失败保留草稿和重试入口。
- 复用已有隔离草稿、命令序列和存储降级规则，不能为了改 toast 另起一套并发保存。可恢复降级保存按实际保障程度提示；完全失败不伪装成功。
- 数据保存不被权限申请或原生排程阻断。持久化确认后可显示「已保存，正在安排提醒」；随后按当前事项、当前版本、当前载体的结果更新反馈。网络或权限页面返回、迟到响应不得覆盖新编辑的结果。
- 状态至少覆盖下表；推荐文案可按实际时间与平台微调，语义固定。

| 条件 | 反馈示例与动作 |
|---|---|
| 当前事项排程已获真实确认 | 已保存，计划明天 15:00 提醒 · 查看 |
| 当前事项正在排程/结果未知 | 已保存，提醒安排尚未确认 · 查看状态 |
| 普通通知所需权限被拒绝 | 已保存，通知权限未开启 · 去设置 |
| 闹钟可排，但通知/屏幕能力受限 | 已安排闹钟，通知显示受限 · 查看设置；不误称完全不响 |
| 只能非精确排程 | 已保存，提醒可能延迟 · 查看设置 |
| 业务总开关关闭 | 已保存，提醒已关闭 · 查看设置；不擅自替用户开启 |
| 排程失败 | 已保存，提醒安排失败 · 重试 |
| 没有明确事项时间 | 已记下，待补提醒时间 · 去整理；另行说明现有整理提醒，不暴露兜底时间为事项承诺 |
| Web/PWA 没有可靠后台能力 | 说明关闭页面后的提醒限制，不显示 Android 的就绪结论 |

toast 消失后，事项详情仍可查相关状态；已知全局断链复用首页告知条。全局状态正常不能证明刚保存的这一条已排成功。错误解除后同步撤销旧警告，手动关闭开关与权限失败分别处理。

### UX-T02 首用设置与测试改成短路径

- 不在首次启动 600ms 后无条件打开整张技术自检表。空首页先允许录入；首次保存需要提醒的事项后，按真实缺口提供可跳过的设置入口，设置中始终可重新进入。
- 按当前载体请求必要能力，一屏一个主要动作；解释「为何需要」与「拒绝后的影响」。已满足的不反复申请，拒绝后仍可使用记录功能。
- 简单路径为「检查必要设置 → 60 秒测试 → 锁屏等待 → 返回查看结果」。由用户主动开始，测试事项独立标识、不开周期、不进入用户正常统计；有停止声振/取消未触发测试入口。
- 测试区区分系统事件证据与「我听到了 / 我看到了 / 没收到 / 不确定」用户反馈；用户未回答不等于失败或成功。单次测试通过只描述本次场景，不显示「后台永久可靠」。
- 旧 `onboardDone` 不等于已通过测试；新引导状态不伪造旧记录。可增加最少量、兼容缺省值的设置字段，升级不能覆盖既有用户设置或重复强制引导。
- 技术诊断、排程详情、环形日志移至「高级诊断」。用户能找到它，但不要求先读懂 token、Capacitor、reconcile。

### UX-T03 先补原生证据回流，再提供事后核查

这是本方案明确列出的必要原生工作，不能仅改文案后声称完成。其目标是正确观察，不改变提醒次数/补投策略。

- 为普通通知、重要/关键及显式闹钟首次事件分别画出「排程 → 接收 → 通知提交/声振请求/窗口可见 → 回到 Web → 持久化」映射，复用可用桥和身份。
- 最小事件身份包含事项 ID、逻辑轮次/提醒键、计划时刻、载体，以及防止过期回写所需的版本/token。时间戳或标题单独不能作为身份。
- 原生在真实阶段写最小持久证据，Web 冷启动/回前台读取并幂等合并。不能只挂 JS 运行期间的监听，也不能只从 150 条易被挤出的诊断日志或「最后一次」结果推断所有事项。
- 证据至少支持次日重开（24 小时后）仍可关联；有明确容量和保留策略，报告实际选值与理由。到期淘汰、环形覆盖、升级前旧数据及缺失字段一律归为 unknown，不能反推失败。避免存标题/正文和凭据。
- 接收可确认时只写「系统已接收」；`delivered` 若沿用，必须明确其技术含义。通知入栏不等于横幅可见，窗口创建不等于可见，声振请求不等于用户听到，均不得写成 ACK。
- 不删除/弱化原本正确的去重语义。旧轮次回执不得覆盖稍后产生的新轮次；完成事项不能因迟到回执复活。与 D69 差量对账、事件持久化失败重试和原生 token 生命周期一起验证。
- 事后展示规则：只针对本版本已登记排程且进入可观测范围的事项，在前台完成证据回读后核查。明确异常显示真实异常；只有缺少证据时用「本次提醒结果尚未确认」，不能说「确定漏提醒」。刚到点/回读进行中显示处理中；迟到证据到达后更新，按事件去重，不每次进入页面弹窗。
- 旧版、被淘汰或未覆盖载体不产生逐项漏报指控；详情说明无法核查。尚无有效证据时宁可 unknown，不设一个任意分钟阈值把 unknown 变为 fail。
- 此项只告知并提供现有「稍后提醒/设置时间」入口，不新增自动补投、自动修改事项优先级、反复唤醒或清空提醒台账。

### UX-T04 OEM 引导只承诺已验证的动作

- 设置跳转返回实际落点。到应用详情页就明确说到了应用详情页，并提供经核对的手动路径；不能标记为已打开自启动授权页或已授予。
- 厂商开关无法读取时显示「需手动确认」，用户勾选只代表用户反馈，不作为程序检测成功。
- 找不到经验证可达的路径时，提示「此系统暂未找到可验证的设置路径」，提供能力说明和测试入口，不能将用户循环送回同一页。
- 不能把本任务变成寻找隐藏权限/绕过签名限制。需要修改个人设备的系统设置、重启或制造冷进程时，按既有明确授权执行，缺少授权只暂停该实验。
- 若要声称某设置解决冷进程问题，必须有同 APK、同设备、同触发条件的修改前/后对照。只验证导航成功，不能声称恢复可靠投递。
- 没找到修复路径时仍可交付诚实的限制说明，但冷进程修复格不得 PASS；这不是全面解决 OEM 后台限制的承诺。

## 5. P2：让第一件事容易记下来

### UX-C01 干净首启与主动演示

- 无数据首次启动不自动 seed，不弹演示提醒。已有数据原样加载，升级不移除旧事项，也不按标题识别并删除旧示例。
- 空首页提供一句用途说明、明显「记一件事」入口和输入示例。未完成/待整理存在时，不误说没有待处理事项。
- 「查看演示」为主动入口，演示明确标识、与真实数据隔离；推荐只读示例预览，不为演示注册任何原生或 Web 通知，不改用户统计。
- 旧「载入示例数据」入口同步改为安全预览，不能遗留可覆盖用户状态的路径。

### UX-C02 默认表单减负，高级能力保持可达

- 默认可见：一句话输入、识别摘要、可点修改时间、保存按钮、「更多选项」。AI 理解/润色、重要程度、截止、项目、周期、周期方式、备注、标签、来源置于更多选项。
- 识别摘要必须展示有效提醒时间，以及已识别的周期/截止等会影响行为的重要信息；不要把解析出的周期藏起来让用户误建重复提醒。清除或手选时间后摘要同步更新。
- 新建默认收起更多选项。编辑已有复杂事项时显示已设置内容摘要，并可一键展开；未改的字段完整保留，不能因隐藏而清空。
- 深链/分享预填保留 URL、备注等字段并显示相应摘要；保存过程中 AI 失败回退本地，解析响应迟到不能覆盖用户手选。
- 明确时间、模糊时间、无时间沿用已有解析与待整理合同。内部 fallback 继续用于既有整理流程，但不显示成「已经替用户定好的提醒时间」。
- 不改变系统键盘支持、中文输入法、焦点、滚动与取消行为。手机键盘打开后输入和保存仍可到达；弹条不能遮住表单的关键操作，处理遮挡不得隐式 ACK 或取消真实闹钟。

### UX-C03 保存后的查看、修改与有限撤销

- 保存后提供查看入口，直接定位刚保存的事项，不要求在整个月历里找。明确时间事项与待整理事项分别进入正确详情/整理入口。
- 新建成功可短时撤销，窗口建议 8 秒；只针对本次创建、当前版本未被后续操作改变、未开始投递的事项。撤销是用户明确动作，不能批量操作其他事项。
- 复用事务命令和原生撤销对账；输入不丢、快速连点不重复。事务提交后方可确认撤销；原生取消失败必须提示旧提醒可能仍存在并允许重试，不能显示完全撤销。
- 已被编辑/ACK/稍后/完成、已投递或无法确认是否进入投递时，拒绝过期撤销并引导查看/修改；不使用整份旧 state 覆盖当前数据。编辑保存提供查看/继续修改，不伪造完整历史撤销能力。

## 6. P3：明确三个动作的后果并提供恢复

### UX-A01 同一动作在不同入口含义一致

| 动作 | 固定语义及反馈 |
|---|---|
| 我知道了 | 停止当前轮次催促，仍未完成；已设置的截止保护继续。ACK 型周期保留既有下一周期推进，不能文案承诺以后不再提醒 |
| 稍后提醒 | 主动建立下一次提醒；展示具体日期/时间。应用内保留现有选择；原生快捷稍后明确标注 2 小时，不能偷换为任意默认值 |
| 完成 | 结束当前实例并归档；周期事项只按既有规则生成下一实例；明确反馈是否存在下一周期 |
| 关闭/停止声振 | 只结束当前展示或声振，不冒充 ACK、完成或稍后；保留既有抑制规则 |

- 首页卡片、详情、弹条、Android 闹钟及通知快捷动作都核对。沿用当前按钮名称，空间允许时加短副说明，不要求用户记住缩写。
- 第一次 ACK 用非阻塞反馈说明「已停止本轮催促，仍未完成」，提供「稍后提醒」入口。后续用短反馈；截止/周期例外在相关事项详情可见。
- 将用户可见 ACK、Capture、NEEDS_REVIEW、Future 等术语替换为中文用途说明；不重命名内部状态和 API。改动限本次触及的用户流程。

### UX-A02 已看到未完成可找回

- 首页折叠入口保留数量与「未完成」含义，展开后可查看、稍后提醒、完成；搜索继续覆盖此池。
- 此类事项不计为完成，不因离开页面/重启/日期变化被归档。设置下一次提醒后立即显示具体时间与保存/排程结果。
- 本次不增加每天催促已确认事项的机制，不启用新的默认摘要。验证几天后的恢复可用，不用新增催促掩盖状态混乱。

### UX-A03 完成后的有限撤销

- 应用内完成成功提供建议 8 秒的撤销入口；主动作即时按既有持久化合同提交，不为撤销倒计时延迟停止声振或延迟存盘。
- 撤销仅覆盖本次完成且相关事项/本次派生周期实例未被后续动作改变的范围。不能把归档列表的「恢复」直接冒充撤销；后者当前有不同的提醒与截止保护语义。
- 对周期事项，撤销要成组还原完成前的业务状态，并回收仅由此次完成生成且尚未处理/投递的下一实例；ACK 之前已经派生的下一实例不得删除。任一受影响实例已变化、排程取消不确定、或发生其他并发操作时，拒绝不安全撤销并说明如何从归档继续处理。
- 不回放已发生的铃声、通知、ACK 或投递证据；恢复后只对未来仍有效的计划按现有规则对账，不能因撤销立即补响已经过去的同次事件。若需最少量抑制元数据，明确其事件身份、生命周期和旧数据缺省值，不能改全局补投规则。
- 原生锁屏/通知中的完成不强行拉起主应用展示 toast。完成前确保用户能分辨按钮含义，误触后可使用既有归档恢复入口；短时撤销只在应用内此次操作的 8 秒窗口提供，不在次日重开重新发一个撤销窗口。
- 撤销失效只失效撤销入口，不影响正常完成；进程重启后保留已经确认提交的最终结果。多次点击、持久化失败及原生动作竞争不能造成重复周期或丢事项。
