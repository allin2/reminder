## 第一阶段：修复编辑丢时间（P1，原因已确认）

### 原因

`app-core.js` 的 `saveItemFromForm()` 在标题变化时重新解析标题。新标题不含时间词会得到低置信度；`finishSave()` 随后的 `parsedLow` 分支丢弃了表单中仍然有效的原时间。编辑页只填充时间框，不把原值视为本次用户手选，因此没有进入 `explicitTime` 分支。

证据：`title-edit-counterexample.json` 中保存前时间为 `2026-09-21T15:00`，保存后 `triggerAt=null`；`title-edit-after-reload.json` 确认缺陷已持久化。

### 建议行为契约

| 操作 | 保存规则 |
| --- | --- |
| 新建事项 | 保持现有自然语言解析、手选优先及模糊时间待整理行为 |
| 编辑标题、备注、标签、项目、优先级 | 未显式修改时间时保留原提醒时间与时间基准 |
| 编辑标题加入新的时间词 | 默认保留编辑页已有时间；改期通过现有时间输入框完成，与“编辑无需重新解析”的界面约定一致 |
| 手动选择新时间 | 采用用户选择，取消旧调度、保存新轮身份、建立新调度 |
| 显式清空时间 | 保存为无提醒；不得用标题重解析或兜底时间补回 |
| 稍后产生的 elapsed 提醒仅改标题 | 保留 `scheduleBasis`、`snoozedAt`、`snoozeDelayMs` 等语义，不静默改为 wall-clock |

### 实施范围

- `app-core.js`：在现有表单会话/冻结草稿中记录时间字段是否被明确编辑，区分“未动”“改值”“清空”；提交时从冻结快照读取。
- 调整 `finishSave()` 的编辑分支，避免用真值回退 `explicitTime || ...` 混淆显式清空与未设置。
- 检查 `applyItemEdit()`：保留未修改时间的完整元数据；真正改期才重置相应提醒轮次。版本推进仍需遵守旧通知防覆盖规则，不能简单停止 `rev` 更新。
- 同时检查截止时间、重复规则等未改字段是否被标题解析旁带覆盖；复用现有字段，不引入新的调度框架。
- `test-regressions.js` / 现有表单行为测试：加入真实编辑入口与重载反例；必要时补 `test-native-reminders.js` 的排程断言。

### 验收

1. 原实机反例先在旧基线失败，修复后通过；保留前后证据。
2. 改标题、备注、标签、优先级均保持未修改时间；保存成功反馈与持久层一致。
3. elapsed 稍后事项仅改标题，剩余时间及基准不漂移。
4. 显式改期后旧时间不响；显式清空后不再有该事项排程；重载和进程重启后结果保持。
5. 双击、异步保存期间关闭重开表单、旧通知动作等现有反例继续通过。

## 第二阶段：定位后台派发失败（P1，先补证据）

### 已知与未知

- 前台已取得约 132 ms 接收及全屏可见证据。
- 其他应用前台与熄屏时，系统闹钟条目的 `adjustment` 被推迟约 3 天，60 秒内未接收。
- 冷进程两次无接收；触发后队列无对应活动条目，不能仅凭消失判断“系统已经派发”。
- “允许后台使用”和全屏通知设置已开启，但这不等于所有厂商自启动/冻结策略均已放行。
- 上轮通过 `logcat -d -t 2500` 截尾取证，未保留完整触发窗口；清空日志也未解决截尾缺口。不得据此断言当前候选存在某条具体厂商拒绝原因。

### 诊断改进

在独立 run 目录保存可复用脚本，排程前启动连续日志流，测试结束关闭本次采集进程。不要再执行 `logcat -c`。原始日志仅本地保存，外发前脱敏。

每条提醒记录：run ID、APK 哈希、item ID/rev、reminderKey、roundBase、trace token、原定时间、实际系统排程时刻、PID、进程状态、屏幕/锁屏状态，以及单调时钟与墙上时钟样本。

按目标时间采集：排程后、退后台/熄屏/终止进程后、到点前、到点后 +3/+10/+30/+60/+120 秒。先取得最后一个未打开 App 的样本，再打开 App 比较是否才开始接收。实时累积 trace，避免环形缓冲覆盖造成假阴性。

以相同包和相同权限完成四组：前台、其他应用前台、锁屏热进程、冷进程。先跑一次定位；改变已确认的相关变量后重复失败组并做前台对照，不进行无目的重复测试。

冷进程测试分别标注正常最近任务划除、系统回收和 `kill -9` 注入；注入不能冒充真实用户路径。不得使用 `force-stop` 作为普通冷启动替代。

### 按结果决定修复

| 证据结果 | 下一步 |
| --- | --- |
| 退后台即出现 +3 天 adjustment，尚无系统派发 | 定位厂商策略触发条件；核对正常设置入口及实际效果。对候选调度方式做单变量实验，未实测前不承诺换 API 能修复 |
| 系统派发后明确拒绝 Receiver/Service 启动 | 查明可操作的自启动/后台限制；只有验证有效的系统引导才进入产品 |
| Receiver/Service 已执行，界面不可见 | 检查通知渠道、全屏/悬浮权限、Activity 生命周期与厂商可见性策略，修复界面链路 |
| 界面显示但无声振或操作后不停 | 检查 `AlarmRingService`、活动投递台账及停止动作链，按相同 token 验证 |
| 目前无可靠的系统允许路径 | 保持该机型场景 FAIL/受限，不宣称送达已修复；单独提出产品限制与替代方案供裁决 |

不要直接采用常驻服务、循环重排、任意超时补响或换成 WorkManager 作为确定修复；这些方案可能增加电量消耗、重复响铃，且没有本轮证据支持。

## 第三阶段：实施经证据支持的原生修复

候选代码范围按诊断结果限定：

- `SystemBridgePlugin.scheduleAlarmInternal()`：当前首次排程入口。
- `AlarmScheduler.schedule()`：恢复/重排入口；两条入口均有排程决策，不能只改其中一处。
- `AlarmTestReceiver`、`AlarmRingService`、`AlarmActivity`：分别对应接收、声振、可见界面。
- 原生 schedule/action/delivery store 与 `lib/native-reminders.js`：身份、取消、幂等及重启一致性。

保留 `scheduled`、接收、通知提交、可见、用户处理之间的区分。不能把过时 scheduled 或空证据直接标为已送达/确定漏响；现有 `unknown/unverifiable` 语义必须保持。补响政策若涉及新的打扰频率和有效期，另列具体提案，不顺带实现。

历史 D70 文档只作线索：其中“没有 delivered 写入者”等结论已可能被当前送达证据实现改变，实施前逐项核实，不照搬旧前提。跨越已有明确产品裁决的改动，按其实际适用范围处理。

## 第四阶段：新候选验收和交付

每次候选使用新目录与新哈希，保留失败候选及原始证据。源码、构建、资源、签名、设备安装包哈希和运行记录需能互相对应。

| 验收层 | 必需内容 |
| --- | --- |
| 开发验证 | 新反例 + `npm test`；改动原生代码时运行 Android JVM 检查与受影响 lint，记录既有失败 |
| 安装包 | 新建 debug 候选，核对 Web 资源、DEX/源码来源、签名与设备 APK 哈希 |
| 前台/后台/锁屏/冷进程 | 当前 token 接收、可见截图及可见台账；保存触发时延，建议核心短时试验目标 ≤5 秒，不能把观察 120 秒内最终到达当作准时 |
| 闹钟动作 | 关闭只止响；ACK 停本轮但未完成；稍后取消旧轮并建立新轮；完成归档；均检查声振、通知、权威持久层及重启状态 |
| 防回归 | 当前实际支持的设备（包括可用 vivo）复核原生改动；没有设备则记 NOT_PERFORMED，不继承旧包 PASS |
| 完整覆盖账 | 对照 `docs/acceptance-cases.md` 逐条回填，不能把本轮 17 组抽样当作全部案例已覆盖 |

重启首解锁前、深度 Doze、跨时区、断网、权限拒绝、分享入口和长期稳定性要分别安排测试窗口。会中断用户设备使用的场景，执行前确认设备处于可测试状态。没有执行的继续标记 NOT_PERFORMED。

交付物：最小源码增量、行为回归、诊断脚本、独立候选、实机报告、逐项覆盖矩阵和哈希清单。测试合成项收尾采用完成/停止重复并复核 pending=0、active=0；不删除用户数据或历史证据。
