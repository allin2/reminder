# 后台送达专项修复方案

状态：待实施；本文件不代表后台问题已修复。

## 目标与依据

目标：在当前 OPPO 上，应用退后台、锁屏及非 force-stop 的冷进程场景，到点后无需打开应用即可产生符合事项级别的提醒，并支持停止、确认、稍后与取消。

依据：`verification-runs/20260920-independent-repair-review/README.md`。当前安装包 SHA-256 为 `de9e63771d3caca0a454562dfd608b44a3d75743a45bff89c4c9ab3b3c19231c`。独立按 token 重算的诊断显示，到点后 120 秒没有接收，打开应用后约 122 秒才收到并显示。编辑保时修复已通过，保留该增量。

当前不能确定唯一根因。优先调查系统实际派发、进程启动与应用接收之间的断点。源码已采用 setAlarmClock，并有广播和前台服务两条唤醒路径；“换成 setAlarmClock”不是新的修复方案。旧注释中的机型实验结论不能替代当前候选证据。

## 阶段一：修复诊断工具，建立可信失败基线

以现有 diag-runner.py 为参考新增版本，保留原脚本及原始证据。

1. 所有本项目设备验证入口使用按设备 serial 的共享互斥锁；检测到未配合的旧 runner 时停止启动新试验，不结束他人的进程。
2. 统一从 itemId/rev/reminderKey 找出所有 trace token，再关联 requested、scheduled、received、ringStarted、windowVisible 等阶段。修正“已经匹配 item 阶段就跳过 token 关联”的假阴性。
3. 排程前和目标时间前后校验屏幕电源状态、锁屏状态、实际前台窗口和 PID。计划为前台但实际 Dozing/锁屏时标记 INVALID_ENV，不算前台产品失败，也不算通过。
4. 生产表单创建独立事项，确认权威保存和原生排程；避免直接修改 state.items 与并发持久化事务相冲突。
5. 保留连续 logcat，不清空日志。采集排程后、场景切换后、到点前以及到点后 +3/+10/+30/+60/+120 秒的 alarm、power、window、进程、trace、delivery 与截图。完成最后一个未打开样本后，才打开应用作补到达对照。
6. 绑定源 SHA/dirty patch、APK 哈希、run ID、设备、用户、权限、itemId/rev/reminderKey/token、计划时间、墙钟和单调时钟。

验证工具至少覆盖：item 阶段存在而 received 的 detail 为空；同事项多 token；历史 token；缺失日志；前台变成锁屏。缺数据输出 UNKNOWN，环境不符输出 INVALID_ENV。

交付：可重复运行的脚本及一组可信失败基线。此阶段完成不算产品修复。

## 阶段二：按断点选择最小修复

| 观测结果 | 修复动作与文件范围 | 阶段验收 |
| --- | --- | --- |
| 系统实际触发时间被推迟，或没有系统派发证据 | 单变量验证系统正常设置入口的后台、自启动、电量限制是否影响当前包；保存前后设置与 alarm 证据。不预设设置一定有效 | 相同 APK、相同场景下开关变量可重复改变结果；有效时才加入具体引导及回到应用后的重新检查 |
| 系统尝试派发，但 Receiver/Service 被拒绝启动 | 根据实际异常修复组件启动、权限检查或前台服务生命周期；定位 AlarmTestReceiver、AlarmRingService 和 Manifest | 不打开 WebView 也能进入接收和服务，连续日志不再出现同一拒绝 |
| 排程成功但系统中的身份、时间或恢复条目不正确 | 检查 PendingIntent 身份、两条调度入口及重排/撤销一致性；限定 SystemBridgePlugin.scheduleAlarmInternal、AlarmScheduler.schedule/scheduleUnfreezer | 初次、恢复、改期、取消使用一致身份；旧轮不响，elapsed 和 wall-clock 语义保持 |
| 已接收/响铃，但没有可见界面 | 检查 AlarmActivity、通知渠道、全屏权限与可见状态写入，按实际生命周期修复 | 同 token 的 windowVisible 或 deliveryVisible 与截图对应；通知提交不算界面可见 |
| 已可见但重复响、停止失败或旧轮覆盖新轮 | 修复投递台账、AlarmRingService 停止逻辑及动作幂等 | 同一轮只产生一次有效提醒；确认/稍后/取消后旧 token 不再恢复 |

若需要实验不同调度方式，每次只改一个变量，使用独立候选，先证明改善且没有重复响铃，再决定是否进入产品。不得直接堆叠新的唤醒路径、循环重排或常驻服务。

如证据不足以定位，追加缺失观测点后重跑失败场景，不能把不确定的厂商策略写成已确认根因。若正常系统能力仍无法满足目标，明确报告该场景受限；任何新增补响频率、有效期或常驻行为另行提出产品方案。

## 阶段三：代码与候选验证

- 修首次排程时同时核对恢复入口，但仅修改被证据证明有问题的部分；保留 IndexedDB 权威数据与原生投影边界。

## 阶段四：实机关闭标准

1. 当前候选覆盖：应用真实前台、其他应用前台、锁屏热进程、非 force-stop 冷进程。正常划除任务与 kill -9 注入分开记录，后者不能冒充正常系统回收。
2. 修复后的失败场景每组至少连续通过 3 次；再增加一次较长等待且确实进入目标省电/空闲状态的检查。前台对照也必须具备真实环境证据。
3. 建议短时重要提醒标准为到点后 5 秒内接收并可见；这是本项目拟采用的验收阈值，不是 Android 平台保证。+120 秒只是诊断观察窗口。原目标若有更严格要求，以既有产品合同为准。
4. 普通提醒按其通知合同验收，重要提醒按全屏/声振合同验收，不能用重要闹钟成功替代普通通知成功。声音以实际听验或录制验证，服务启动日志不能单独证明有声。
5. 检查当前 token、非零 shownAt、可见台账及截图；到点前不打开应用。打开后补到达判为延迟失败。
6. 验证停止、确认、稍后、改期、取消、恢复后不重复；涉及开机恢复的改动必须补手机重启前后的真实检查，WebView reload 不能代替。
7. 仅完成本轮确切测试事项并核对残留排程；保留日志、失败样本及身份清单。

最终交付：源码改动、测试结果、新候选、四场景证据矩阵与剩余限制。只有行为和证据同时满足时，才关闭“后台送达尚未通过”。
