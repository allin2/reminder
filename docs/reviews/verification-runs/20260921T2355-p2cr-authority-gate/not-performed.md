## 1. 后台回收（LMK / `am kill`）

- 目标行为：进程被**平台回收**（后台内存压力路径）后冷启动，权威状态不受影响。
- 尝试与观测：HOME 退后台（确认前台已是 launcher）→ `am kill --user 0 <pkg>` → `am kill-all`；
  **两次之后 `pid` 都仍是 11596**。`dumpsys activity processes` 显示该进程与 WebView 的
  sandboxed 进程存在绑定（`ConnectionRecord … flags=0x80000041`），AMS 因此视其为「不可安全杀」。
- 未执行原因：在本机（ColorOS / Android 16）上**无法让 AMS 选中该进程**，构造不出「平台回收」这一具体路径。
- 替代证据：LMK 的终止手段同样是**内核 SIGKILL**（无优雅退出），而 **SIGKILL 已独立验证 PASS**
  （用例 3：A==C、死亡窗口静止、恢复判定 `loaded/authoritative`、`blockedWriteCount=0`）；
  另有 3+2 轮 `force-stop → 冷启动` 与 SIGKILL 轮合计 **6 次冷启动，记录级哈希全部不变**。
- 保留意见：本条**不因替代证据转为 PASS**，仅在「终止方式」维度上把 SIGKILL 作为等价终止手段记录。

## 2. 桥初始化失败（冷启动时原生桥不可用）

- 目标行为：原生桥初始化失败时，权威数据的**判定与保护不受影响**（不写、不丢、不误判首启）。
- 未执行原因：要让**冷启动那一刻**原生桥不可用，需要改包（去掉/改坏插件实现）——
  而改包即失去本 run「真机跑的就是本批源码」的逐字节等价性前提；不改包则没有可用手段
  （`waitForNativeBridge` 的失败分支需要桥在数秒内始终不出现，不 rudimentary 的平台操作可稳定构造）。
- 替代证据（带牙齿，自动化）——组合 harness 注入桥故障（`test-boot-combination.js` B5 ⑦，8 条全绿）：
  1. **注入真的命中**（被点名的方法被调用且拒绝，`calls.faultHits>=1`，不是只改了配置）；
  2. 桥故障 + 权威健康 1/1 ⇒ 应用**仍然就绪**（`initializeNativeReminders` 的 catch 兜住）；
  3. 桥故障不改变权威判定（仍 `loaded/authoritative`、`writesAllowed=true`）；
  4. 桥故障后**旧数据完好**（IDB 仍是那 1/1，没有空态覆盖）；
  5. 桥故障 **+ 权威读失败** 叠加 ⇒ 判 `failed`、`writesAllowed=false`；
  6. 叠加故障下**仍然一笔不写**（`puts=0`）、不留待回放凭据、旧 IDB 逐字节未动；
  7. 叠加故障下**既不排通知也不起业务心跳**；
  8. 叠加故障下**恢复面板照样出现**。
- 另有静态证据：`initializeNativeReminders()` 整段在 `try/catch` 内，
  失败时置 `nativeReminderStatus.reliability="error"`（app-core.js 的 catch 分支），不向数据面扩散。
