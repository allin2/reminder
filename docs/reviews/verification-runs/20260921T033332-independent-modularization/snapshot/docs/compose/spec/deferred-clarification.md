# 延迟澄清（Deferred Clarification）

## Report

**交付状态** — **规格已定，五处行为待改。** 按
[交互逻辑决策清单](../../decisions/interaction-logic-2026-09-16.md) 的 D4，代码改动单独一轮。
**2026-09-16 已按 V0.2 冻结基线复核，下方数值均为复核后的版本。**

**现状** — 主体**已经实现**：`detectNeedsReview()` 负责标记，`NEEDS_REVIEW` 负责承载，
`openReviewSession()` / `renderReviewCard()` 负责批量澄清，`maybeReviewSession()` 负责窗口调度。
本规格确认这套设计，并修正五处偏差：

| 偏差 | 现状 | 应改为 |
|---|---|---|
| 兜底值 | `now + 7 天` | **下一个 Review Window**；Review 关闭时退次日晚间（D17） |
| 兜底到点行为 | 正常晋升 `due`、进首页、发通知 | **不进首页、不发事项提醒**，只再推一次整理（D17） |
| 入口形态 | 首页入口**常驻且置顶带数字** | **常驻弱入口**（无数字、无强调色、移到「需要注意」之后）；窗口 ∪ 宽限期内恢复显著性（D6, D20） |
| 唤醒通道 | `SystemBridge.scheduleAlarm` → **全屏闹钟** | LocalNotifications 普通通知（D19） |
| 补提醒参数 | 45 分钟 × 1 次 | **60 分钟 × 2 次**（当天最多 3 次）（D22） |

（另有一处不受影响但需保留：提醒**受「本地通知」总开关控制**并按普通事项参与勿扰 —— D18。）

## [S1] Problem

用户在刚说完一句话的那一刻最不想做判断。PRD §10 原先要求低置信度「进行一次极简选择」，
等于把判断压在捕获现场；而不做确认又会留下不知道时间是什么时候设的、也不知道自己确认过没有的
记录。两难要用**时间差**解决，不是用更多弹窗。

## [S2] Design

### [S2.1] 标记规则

命中任意一条即标记 `review_status = "NEEDS_REVIEW"`：

- 用户手动保留；
- 解析不出任何时间；
- 解析置信度为 `low` / `none`；
- 内容过于模糊（「看看这个」「研究一下」「以后看看」）；
- 只有 URL，既无标题也无备注。

### [S2.2] 捕获永不失败

**主路径不弹确认框。** 低置信度直接保存并标记，提示改为「已收下 · 待整理」+「去整理」。
高/中置信度仍走正常路径。

**但保留「极简选择」能力**（V0.2 §6.1「仅在必要时给极简选择」）。判定「必要」的唯一条件：

> **输入里含具体时间指向词**（明天 / 后天 / 下周x / x月x日 / 月底 / N 天后 / 上午x点…），
> **但解析器仍落到兜底值**。

这是真正的矛盾——用户说了时间、系统没听懂。其余低置信度（「过阵子」「以后」「回头」这类
本来就模糊的词）一律静默收下，不打断。

### [S2.3] 兜底时间语义（D17）

没有时间的待整理记录，`triggerAt` 兜底为**下一个 Review Window**；若 Review 已关闭，
退到**系统默认次日晚间**。兜底之后：

- **不参与 `promoteDue()`** —— 永不进入 `due`，永不进首页「需要注意」；
- **兜底时间不发提醒**；
- 到点只**再推一次整理**。

理由：它不是一条事项，是一笔还没结清的账。让它以正式提醒的身份出现，等于让用户面对一条
自己从未确认过、也不知道时间来源的东西。

### [S2.4] 窗口与入口形态（D6 + D20）

入口**常驻**，但分两档显著性：

| 项 | 规则 |
|---|---|
| 整理窗口 | 默认每天 21:30–23:00，可配置 |
| **弱形态**（窗口外平时） | 一行低对比度文字「待整理」，**不带数字**、不加强调色；位置在「现在需要注意」**之后** |
| **显著形态**（窗口内 ∪ 宽限期） | 带数字「待整理 · N」、提到首页最前 |
| 宽限期 | `snoozedUntil` 到期后 **1 小时内**保持显著形态（覆盖「稍后」跨出窗口的情况） |
| 无待整理时 | 完全不渲染（避免常驻一个空入口） |

V0.2 §12 的原话是「弱入口…**仅在 Review Window 或用户主动进入时提高存在感**」——注意它说的是
**提高存在感**，不是"出现"。所以弱形态常驻、窗口内变显著，才是这句的准确落地。

### [S2.5] 唤醒通道与参数（D19 + D18 + D22）

- 用 **LocalNotifications** 预排一条普通通知（`importance` 与「重要」档同级即可），
  **不再使用 `SystemBridge.scheduleAlarm`**；
- 补提醒参数：**60 分钟间隔 × 2 次（当天最多 3 次）**，达上限后滚入下一个窗口；
- 受「本地通知」总开关控制：开关关闭则取消待整理提醒；
- 按**普通事项**参与勿扰：勿扰覆盖到窗口起点时顺延；
- 复用 LocalNotifications 意味着自动继承开机恢复、应用更新恢复、权限对账，无需第二条排程路径。

### [S2.6] 通知点击直达会话（D20）

通知点击必须**直接打开整理会话**，不得只打开首页让用户自己找入口。
这是兜底：即使入口因为窗口规则不可见，通知也永远能到达它所说的那件事。

### [S2.7] 卡片内容与动作（D16）

每条卡片必须展示：

- 原始记录（用户当时写的原话）；
- **系统解析结果**——无时间时必须显示「**系统解析：未设定时间**」，不得让兜底时间成为隐性决定；
- 来源：来源标题 / URL / 来源 App / 记录时间。

动作：**删除 / 确认 / 保存修改**（可改标题、提醒时间、备注）。
会话出口：稍后（30 分钟 / 2 小时 / 今晚 / 明天 / 下一个整理时间）、跳过本次、完成。

### [S2.8] 与首页、归档的关系

- 待整理的记录**不占用**「需要注意」的位置，也不计入 Badge；
- 语义是「信息尚未二次确认」，**不是**逾期任务；
- 首页入口的副标题必须写明这一点。

## [S3] Out of Scope

- 用 AI 判断"这条到底算不算模糊"（当前用确定性正则与置信度）
- 自动合并相似记录（PRD §23 明确禁止自动合并）
- 跨设备同步待整理队列
- 待整理使用全屏闹钟（**明确禁止**，见 [关键档全屏闹钟](./android-fullscreen-alarm.md)）
