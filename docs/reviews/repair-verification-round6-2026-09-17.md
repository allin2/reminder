## I1 复核结果

当前 runCommit 对写入排队，并在出队时取快照；commitActionOnce 把失败回滚放入同一队列任务。它修复了上一轮“A 动作先进入空队列、B 普通保存随后进入”的复现。

但 performAlarmAction 仍在进入队列之前修改共享 state。已有排队保存请求会看到后来的未提交动作，因此还不能把该机制称为完整事务隔离。

## J1 · P1 · 先排队的普通保存会提前提交后到的 ACK

位置：`app-core.js:566`–`:581` 的提交队列、`:3492`–`:3498` 的同步状态变更、`:3517`–`:3518` 的动作提交排队；快照读取位于 `:539`–`:542`。

### 独立复现

使用当前 test-regressions.js 的真实应用/存储适配器和 createDisk mock，等待 boot 完成；只在内存拼接探针，无源码或测试文件修改。

1. 创建周期 ACK 事项 A、普通事项 B，持久化初始状态。
2. 发起普通保存 S0，扣住其提交完成回调。
3. 用户完成 B，保存 S1 排在 S0 后。
4. A 收到 ACK 动作：立即修改共享 state、生成下一期、写内存事件台账，动作提交 S2 排在 S1 后。
5. 按 FIFO 顺序让 S0、S1 成功。S1 出队时取快照，已包含 A 尚未提交的 ACK。
6. 让 S2 失败，等待动作回滚；使用同一模拟磁盘重新启动应用。

实测：

```text
S2 完成前：磁盘 A=acknowledged，items=3，事件台账=true
S2 失败后：内存 A=due，items=2；磁盘 A=acknowledged，items=3
重启后：A=acknowledged，items=3
```

所有提交按创建顺序释放，没有依赖数据库乱序。较早的 S1 将较晚的 S2 状态提前保存，S2 的内存回滚无法撤回它。该场景允许 S0 长时间待提交，B 操作和 ACK 不需要发生在同一个 JavaScript 调用栈中。

### 修复建议

隔离必须覆盖业务变更与提交，不能仅覆盖写快照和回滚。把动作校验、状态变更、派生、事件台账及提交放入一致的串行操作边界，或基于已提交状态构造隔离草稿，避免较早保存读到后来的未提交变更。普通用户操作也须有明确的合并/重放规则，保持 H1 的“不丢后续操作”。

新增验收：队列非空时“普通保存 → B 完成 → A 周期 ACK”，前两笔成功、A 失败，重载后必须 A=due、无下一期、无 A 已处理标记，B=archived；同时保留原 I1 空队列、同事件并发、两笔成功与镜像失败回归。仅增加一次失败后补存不足以证明崩溃窗口内的一致性。
