## N1 · P1 · 重放 ACK 未撤销首次 ACK 的派生结果，生成两个下一期

位置：`app-core.js:667` 的 replayUserOps、`:3516` 的 rollbackItemTransaction、ackItem/spawnNextInstance。

回滚仅撤销 txn.created 中由原生动作自己生成的实例；用户在提交期间执行的 ACK 也会生成下一期，但它的派生实例不在 txn.created 中。回滚还原源事项后，replayUserOps 又执行一次 ACK，生成新的实例，首次用户 ACK 的实例却仍留在 state.items。用 touched 过滤无关事项只能避免重放无关操作，不能消除相关操作第一次执行的副作用。

### 独立复现与重载

复用当前 test-regressions.js 的 createApp/boot/createDisk 与真实 app-core.js、storage.js，只在内存拼接探针，无产品或测试文件修改。

1. 保存一条 due 的 ACK 模式每周周期事项 A。
2. 调用 handleAlarmAction(snooze)，扣住数据库提交。
3. 普通调用 ackItem(A)，模拟用户点击“我知道了”；首次生成下一期，items=2。
4. 让 snooze 提交失败，等待回滚与重放；再让 ACK 的保存成功。
5. 使用同一模拟磁盘重新启动应用。

实测：

```text
回滚前：items=2
回滚后：A=acknowledged，items=3，两个不同 id 的 waiting 下一期
重启后：items=3，next=2
```

本次探针中两个下一期的 triggerAt 也不同：第一次按尚未提交的稍后时间计算，重放按还原后的时间计算。旧派生实例因此不仅重复，而且保留了失败动作造成的时间影响，将导致多余提醒和周期分叉。

### 修复建议与验收

重放必须基于没有包含被重放操作首次副作用的状态：记录并撤销该操作的完整变更集合，或使用稳定操作/派生身份和幂等重建，或统一串行执行相关业务动作。不能只还原源事项、保留原派生结果，再调用会生成随机新 id 的业务函数。

新增验收：“周期事项原生稍后提交中 → UI ACK → 稍后失败 → ACK 保存成功 → 重载”，必须恰好保留一个按有效状态计算的下一期，失败事件不留已处理标记。补测相关用户完成操作的周期派生、多次相关操作及其对派生实例的修改，防止撤销副作用时丢失用户后来的操作；保留无关事项不被重复重放及 M1/K1/I1/J1 回归。
