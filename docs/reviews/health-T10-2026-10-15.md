## 发现的问题（按严重度排序）

### P1-① 跨版本导入的失败提示对用户不友好，且与该改动实际触发原因不符
- **违反条款**：INV-09（数据库是事实来源、可重建）的兼容面；提示文案可用性（§5 报告口径）
- **复现步骤**（Node 复现，无需浏览器）：
  1. `git show HEAD:lib/app-backup.js > /tmp/old-app-backup.js`（取 HEAD 提交版验证器）
  2. 构造含 `lost` 台账的载荷（工作区新版导出），用**旧验证器**校验：
     `oldBackup.validateBackupPayload(payloadWithLost, 5)`
  - 实测输出：`ok:false, code:"unknown-key", path:"items[0].reminderEvents[\"x@lost\"].lostAt"`
- **期望**：提示应指向「版本差异」（如「这份备份来自更新版本，请先更新应用」），或至少给出可理解的说明
- **实际**：走通用分支 `导入失败：备份格式不正确（items[0].reminderEvents["x@lost"].lostAt）`（`lib/app-backup.js:772-783` 的 `importFailureMessage`，`:783` 兜底分支）。路径是**内部字段路径**，普通用户看不懂；且拒绝的触发点是**新增键** `lostAt`（`REMINDER_EVENT_KEYS`，`lib/app-backup.js:153` 工作区版才加入；旧版无此键 ⇒ 先报 `unknown-key` 而**不是**任务书预期的「旧版只认 4 种台账 state」）。任务书预期需修正。
- **证据**：`/tmp/t10-check.js` 输出 H 段；`lib/app-backup.js:153-155`（工作区 `REMINDER_EVENT_KEYS:153` / `REMINDER_EVENT_STATES:155` 新增 `lostAt/lostReason` 与 `lost`）、`:772-783`（`importFailureMessage`）；HEAD 提交版同处 `REMINDER_EVENT_STATES` 仅 4 项、`REMINDER_EVENT_KEYS` 不含 `lostAt/lostReason`
- **影响面**：任何把新版备份导入旧版/未升级客户端的用户；只发生在「新版→旧版」单方向
- **补充事实**：`lost` 状态属**未提交改动**（HEAD 提交版的 `REMINDER_EVENT_STATES` 只有 4 项，工作区才含 `lost`）。若在提交前发布，会同时造成「旧版吃不到新格式」。旧备份→新版方向实测兼容（`ok:true`）。
- **建议修复**：`importFailureMessage` 增加一类「疑似版本差异」（如命中 `reminderEvents.*.lostAt` 或缺键即提示升级）；发布前确认 `lost` 相关改动已提交并复核 SW 缓存版本
- **验证方式**：重跑 `/tmp/t10-check.js` H 段

### P2-① IndexedDB 不可用时的降级「有时不告知」
- **违反条款**：INV-06 / §305「关键能力不得偷偷降级而不告知」的**持久化面**（非提醒能力）
- **复现步骤**（Node）：`storageMod.createStorage({})` + 环境无 `indexedDB` 但有 `localStorage` → `load()` 后 `backend==="local"`；再经 `createAppPersistence(...).loadAsync()` 实测返回 `status:"loaded", reason:"authoritative"`，**没有任何失败/降级提示**（对比：IDB 存在但 `open()` 抛错时返回 `status:"failed", reason:"authoritative-backend-degraded"`，会显示恢复面板）
- **期望**：只要权威后端不是 IDB，就应以可见方式告知（哪怕是一句「当前为浏览器存储，容量受限」）
- **实际**：`lib/app-persistence.js:47` 的 `authoritativeBackendMissing` 要求 `hasIdb()===true` 才判降级；「根本没有 IDB」时 `hasIdb()===false` ⇒ 视为正常权威（`:153,159,160`）
- **证据**：`/tmp/t10-check.js` G 段；`lib/app-persistence.js:47,153,159-160`；`lib/storage.js:16,93,106-119`（`:116` 选定 `local`、`:119` 兜底 `memory`）
- **影响面**：禁用 IndexedDB 的浏览器/隐私模式；数据仍在，仅持久化后端降级
- **建议修复**：`authoritativeBackendMissing` 放宽为「IDB 可用性判定为假、或后端≠idb 且非首启」等，使其与「读到旧数据」区分

### P2-② 既无 IndexedDB 又无 localStorage（memory 后端）时静默运行，刷新即丢数据
- **违反条款**：INV-09（数据库为事实来源）+ §305；严重度按定义接近 P0/P1，但触发环境罕见，暂记 P2 并显著标注
- **复现步骤**（Node）：删除 `global.indexedDB` 与 `global.localStorage` → `storageMod.createStorage({}).load()` ⇒ `backend==="memory"`；经持久层 `loadAsync()` 实测 `status:"empty", reason:"authoritative-empty", writesAllowed:true`
- **期望**：应阻断启动或明确告知「本机无法持久化，刷新会丢数据」
- **实际**：应用照常启动、允许写入，数据只落进程内存，刷新即丢，全程无提示
- **证据**：`/tmp/t10-check.js` G 段 Case C；`lib/storage.js:119`（`backend="memory"` 兜底）；`app-core.js` 未见 memory 后端告知（`app-core.js:134,2365-2468,3728` 的恢复面板仅覆盖 `status===failed`，不覆盖 `backend==="memory"` 的 `empty` 态）
- **影响面**：storage 被完全禁用的极少数环境；命中后果为静默数据丢失
- **建议修复**：给 memory 后端加启动级告知/阻断
- **验证方式**：`localStorage` 与 `indexedDB` 同时 prohibited 的浏览器配置

## 已知问题复核（任务书第 4 节相关条目）

- **P2-⑯ 幽灵闹钟**：**仍存在**（复核确认，非新问题，不重复上报为独立发现）。机理：JS 侧对账只撤销 `settings.scheduledAlarmIds` 里的 id（`lib/native-reminders.js:740-779`），而原生在 `PREFS_SCHEDULES` 里另有**自己的持久计划**（`SystemBridgePlugin.persistAlarm` / `restorePersistedAlarms`，`:207,226-266,467+`）。当清掉 localStorage/换新浏览器配置使 JS 台账为空时：`prev=[]` ⇒ `stale=[]` ⇒ **不会**撤销任何原生已排/已持久化的闹钟；重启后 `restorePersistedAlarms` 甚至可能把「已在 JS 里删除」的闹钟重新武装 ⇒ 幽灵闹钟（HC-T10-3 场景成立）。判定：**未修**，与第 4 节状态一致。
- **（顺带）P0-② `lost` 状态**：实现存在，但**尚未提交**（HEAD 提交版无 `lost`），且与新备份格式耦合（见 P1-①）。属「部分落地/待提交」。
