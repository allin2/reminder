## 2. 阻断问题及复现

### R-F06 / P1：旧轮台账仍可把新轮显示为“系统已接收”

位置：`lib/delivery-evidence.js:176–195`；相关生产路径 `app-core.js:snoozeItem/applyReminderEvents`。

返工只要求回执键存在于 reminderEvents；但真实稍后与对账流程会保留原定时间晚于新 triggerAt 的旧键，包括 cancelled 键。因此“登记过”不能证明“属于当前轮”。itemRev 和 token 虽被读取，合并时并未用于当前轮身份核验。

独立探针 X1 使用生产入口登记旧轮首次及追提醒 → 稍后到 5 分钟后 → 对账登记新轮并取消旧追提醒 → 在模拟的旧追提醒时刻回读旧轮回执。此时旧版本 1、新版本 2，旧键仍在台账且是 cancelled。结果 `applied=1`，当前事项显示 `delivered / 系统已接收这次提醒`，新轮自身没有接收证据。

这是受控迟到/过期回执场景，不声称已在设备上实际出现。它证明应用不能隔离旧事件，违反 UX-T03。不能只把 cancelled 排除来代替轮次身份：已 delivered 的旧记录、相同时间重排和乱序回读也须覆盖。

修复验收：排程登记和回执共享稳定轮次身份；旧事件可保留历史但不能抬高当前轮核查状态。新增测试必须通过真实 snooze/edit + applyReminderEvents 构造旧台账，覆盖旧 scheduled/cancelled/delivered、同时间重排、重复与乱序、非排程字段编辑。不能机械要求所有事项 rev 相同而误拒合法证据。

### R-F03 / P1：AI 迟到响应仍覆盖新草稿，造成内容串写

位置：`app-core.js:4218–4232`，及 finishSave 对当前表单的读取。

独立探针 X2：启用 AI 自动理解 → 保存“明天下午3点提醒我取快递”，暂停网络响应 → 用户继续输入第二条草稿及“第二条的备注” → 返回第一条的 AI 结果。

结果：第二条输入被清空；已持久化第一条标题为“取快递”，备注却是“第二条的备注”。没有连接外部服务，网络由受控 Promise 模拟，运行的是生产 AI 回调与保存路径。

原因：响应回来先无条件 applyAiToForm，再用可变的当前表单生成保存内容；草稿签名在此后才创建，已经无法识别被污染的表单。现有签名保护只覆盖持久化回调，不覆盖此前 AI 异步窗口。AI 失败回退也读取当前表单。

修复验收：提交时冻结完整草稿与表单会话身份；AI 成功和失败都只处理该提交快照。只有原会话未继续修改时才允许回填/清空 UI。补测慢响应、拒绝响应、关闭重开、连续两次不同内容提交，断言字段与落库内容均不串写。

### R-F07 / P2：停铃读取失败被解释为“没有正在响”

位置：`app-core.js:6293–6307`。

独立探针 X4：activeAlarmDeliveries 抛错、cancelAlarm 正常返回。结果仍写 stoppedAt，显示“没有正在响的测试铃声 · 已取消未触发的测试”。读取失败只能说明未知；取消未来 PendingIntent 不能证明当前铃声已停。stopAlarmDelivery 抛错或返回 false 的分支也没有可靠的成功核查。

修复验收：区分成功停止、确认无活跃投递、读取/停止/取消失败。未确认时给重试，不宣称已停/不存在；stoppedAt 不冒充成功证据。桥失败、token 变更和重复点击分别测试，并在目标设备确认实际铃声停止。
