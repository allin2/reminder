## P1-A · P1 · 保存期间新建的普通事项会被回滚删除

位置：`app-core.js:3518` 的 rollbackItemTransaction；`:2957` 的新建表单 state.items.push。

回滚会删除不在事务基线内的全部事项，但 saveItemFromForm 的新建分支没有通过 runUserOp 记录；因此用户在等待闹钟提交期间新建的普通事项也被删除，重放日志没有任何操作能恢复它。

独立复现使用真实新建入口：保存事项 A → 扣住 A 的原生 snooze 提交 → 表单输入“明天下午三点提交材料”并调用 saveItemFromForm → A 提交失败 → 新建保存成功 → 同一模拟磁盘重载。

```text
新建后：[original, 提交材料]
回滚后：[original]
重启后：[original]
```

用户已收到新建成功反馈，但整条事项及其提醒被静默丢失。D38 所述“期间新建事项会重放出来”目前不适用于真实表单新建入口。

建议：将实际新建入口及所有会被全量回滚覆盖的用户写入纳入完整操作日志，记录已解析字段和稳定 id，或收窄回滚范围以保留未记录的新建。补测真实表单新建、连续新建及新建后编辑/删除，并验证重载结果。

## P1-B · P1 · 重建派生实例后，编辑重放仍写旧对象，编辑结果丢失

位置：`app-core.js:2901` 的 runUserOp(applyItemEdit, [editing, ...])，`:667` 的 replayUserOps。

编辑日志保存的是 editing 对象引用。全量回滚删除派生实例，重放 ACK 时创建新对象并复用旧 id，但后续编辑重放仍把字段写到已离开 state.items 的旧对象。复用 id 能修复 snoozeItem(id) 等按 id 查找的操作，却不能修复直接持有对象引用的 applyItemEdit。

独立复现：周期 A 的原生 snooze 提交中 → UI ACK 派生 N → 用真实编辑表单将 N 标题改为“下一期已修改标题” → snooze 提交失败 → 后续保存成功 → 重载。

```text
回滚前 N.title=下一期已修改标题
回滚后 N.title=每周复盘
重启后 N.title=每周复盘
```

派生实例仍在且 id 相同，但用户保存的编辑内容被丢弃。

建议：操作日志以稳定 id 和不可变参数描述编辑；每次重放按 id 解析当前对象，不保留可能被回滚替换的对象引用。补测“派生 → 编辑 → 再稍后/完成”的组合，确保重建后的实例保留全部后续操作。
