## 0. 真机实锤：首轮 P0-① 在测试机上真实存在

`adb shell dumpsys notification --noredact` 读到测试机上线上包（v1.3）的闹钟渠道属性：

```
NotificationChannel{mId='attention-alarm-v4'
 mImportance=4
 mSound=android.resource://space.alliswell.inbox/2131558400
 mVibrationEnabled=true
 mAudioAttributes=AudioAttributes: usage=USAGE_ALARM ...
```

D59 的设计要求这条渠道**无声、无振动**（声音由 AlarmRingService 自己播），但设备上实际是**带闹钟铃声 + 振动**，即被 `SystemBridgePlugin` 的通用模板抢先创建了。**线上版本在这台机上具备「渠道播一路 + 服务播一路」的双响条件。** 这也证明首轮修复里「整体换到 v5 并退役 v4」是必要的：只删代码、不换 id，已安装设备上的 v4 永远改不回来。

## 二、新发现的问题

### P1

**A-1 页面整体上移、下半屏空白（影响所有窄屏用户，含 Android WebView）** — 新发现，已确证
- **现象**: 打开记录面板、稍后面板等底部面板后再关闭，整个应用上移约 320–380px，下半屏留出空白；底部导航被顶到屏幕中部，点击错位。本次实测中先后由「记一件事」和「稍后」两个面板触发，后者不涉及键盘。
- **根因**: 收起的面板（18 个 `.sheet`）是 `position:absolute` + `translateY(110%)`，它们推到视口下方，把文档撑高到 1679px（视口仅 844px）。`body{overflow:hidden}` 只挡住用户手动滚动，挡不住浏览器为聚焦元素做的程序化滚动。滚动发生后没有任何代码把它滚回去。宽屏（≥480px）下 `#app` 有 `overflow:hidden`，所以桌面上看不到这个问题，窄屏才有。
- **修复验证**: 在页面上给 `#app` 临时加 `overflow:hidden` 后，文档高度回到 844px，聚焦输入框后 `scrollY` 保持 0。
- **建议修复**: 把 `#app { overflow: hidden; }` 从 `@media (min-width:480px)` 挪到基础样式（[index.html:67](../../index.html#L67)）；保险起见，在面板关闭时补一次 `window.scrollTo(0,0)`。

**A-2 重提醒计数在 Android 上会偏少**（P1-⑧ 新功能）
- `realertProgress` 读的是 `it.remindCount`（[app-views.js:31](../../lib/app-views.js#L31) 附近），这个值只在**应用内前台提醒 tick** 里递增（[app-alerts.js:249](../../lib/app-alerts.js#L249)）。Android 上的追提醒由原生 LocalNotifications 在后台送达，不会回写 `remindCount`。
- **后果**: 用户被连环催了 3 次，打开 App 看到的仍是「第 1/4 次」，这和「状态可见性是信任基础」的初衷正好相反。
- **建议**: 计数取 `max(remindCount, 当前轮 reminderEvents 中已过点的键数)`。台账已经按轮次记录了每一次原定提醒，可以直接复用。

### P2

**A-3 内部术语直接露给用户**: 未来页列表底部显示「Future 默认不占据首页。默认隐藏 ≠ 不允许查看。」，这是设计文档语言，不是给用户看的文案。

**A-4 「很重要」不识别**: 输入「…，很重要」后，标题原样保留「很重要」，优先级也没有自动设为重要。用户自然会这样说，但系统没接住。

**A-5 记录面板的时间信息重复**: 解析成功后同时出现「已设置：明天 15:00 · 可修改」和「提醒 明天 15:00」两行，说的是同一件事。

**A-6 删除确认按钮不是危险色**: 确认删除用的是主色（深蓝实心）「确定」，与普通确认无法区分。建议用 `--critical` 并把文字改为「删除」。

**A-7 次级「修改/删除」按钮高 36px**: 低于 44px 惯例。「删除」位于「完成」正下方，慌乱时有误触的可能；有二次确认和 8 秒撤销兜底，所以只列为 P2。

**A-8 删除正在响铃的事项不会自动止响**: 删除只触发对账撤销**未来**的排程，正在响的那一次要靠活动闹钟面板（「原事项已不存在，仍可停止声振」）或自动止响。有兜底，但体验上不连贯。

### 3.2 P0-② 修复的边界风险

**B-1（已排除）证据淘汰误判**: 证据库上限 300 条 / 7 天。只有在 App 一次都没打开、期间又响过 300 次以上闹钟时，才可能因为证据被淘汰而误判，可以忽略。

**B-2（建议收紧）非精确模式下可能误判丢失 → 重复提醒**
- 「无接收证据」判据的阈值是过点 10 分钟（`LOST_NO_EVIDENCE_AFTER_MS`）。精确闹钟权限被拒绝时，闹钟降级为非精确；Doze 下非精确闹钟可能被推迟 10 分钟以上，Android 12+ 上甚至接近 1 小时。
- 这种情况下，App 回前台会先把它判为丢失、补发一条通知；原闹钟之后照样到达 → **同一次提醒响两次**。
- **建议**: `reliability === "inexact"` 时把阈值提高到 60 分钟或不启用证据判据；补发时同时撤掉该键对应的原生闹钟。

**B-3（遗留）普通通知载体仍可能静默丢失**: 普通档的首次提醒和所有追提醒走 LocalNotifications，没有原生接收证据。强停后这些提醒仍会停在「待定」。首轮只修了闹钟载体，这一项要么给通知载体补接收回执，要么在产品上接受这个限制。

### 3.3 Android lint 的 11 个 Error（逐条核实）

| 位置 | lint 结论 | 实际情况 |
|---|---|---|
| SystemBridgePlugin.java:709–727（7 条 NewApi） | 渠道 API 需要 26 | `createChannelIfMissing` 只从带 `SDK_INT < O` 守卫的 `ensureChannel` 调用，属误报；加 `@RequiresApi(26)` 即可消除 |
| DeliveryEvidenceStore.java:109（NewApi） | DE 存储需要 24 | 外层 `catch (Throwable)` 兜住了 API 22–23 上的 `NoSuchMethodError`，属误报；同样可用版本判断消除 |
| AlarmActivity.java:606（MissingSuperCall） | 返回键没调用 super | 刻意设计（D12：返回＝只止响）。**提示**：将来把 targetSdk 升到 36 后，预测性返回不再走 `onBackPressed`，需要改用 `OnBackPressedCallback` |
| AlarmActivity.java:217（WrongConstant） | 用了 `== 0` | 语义等同 `View.VISIBLE`，换成常量即可 |

结论：没有真实缺陷，但 lint 门禁当前是红的。建议一次性消除，否则以后真的 lint 错误会被淹没。

## 五、上线前检查清单

1. **修 A-1**（一行 CSS）—— 窄屏全员可见，优先级最高；
2. **收紧 B-2**（非精确模式阈值）—— 否则 P0-② 修复会在权限被拒的设备上制造重复提醒；
3. **修 A-2**（重提醒计数取台账）—— 否则新功能在 Android 上说错话；
4. **升版本号**: versionCode 4 → 5。渠道 id 变更、台账新增 `lost` 状态都需要一次可追溯的版本；
5. **注意备份降级兼容**: 新版本导出的备份可能含 `lost` 状态，旧版本（1.3）的导入校验只认 4 种状态，会拒收。不打算支持降级可以不管，但要知道有这回事；
6. **真机回归**（vivo V2238A）:
   - 装新包后 `adb shell dumpsys notification | grep attention-alarm`，应只有 v5，且无 sound/vibration；
   - 排一条 2 分钟后的关键事项 → `adb shell am force-stop space.alliswell.inbox` → 过点 10 分钟以上再打开 App，应收到补发通知 + 「N 条提醒没能按时响」toast；
   - 重跑 10s/60s/120s 锁屏闹钟延迟实测，确认没有回归；
   - 让重要事项在后台追提醒 2 次后打开 App，看 A-2 的计数。
7. **lint 清零**（3.3）。
