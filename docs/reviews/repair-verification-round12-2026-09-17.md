## T1 · P1 · 原生 ACK 自己创建的下一期被用户改期后，失败回滚仍将其删除

位置：`app-core.js:3592` 的 rollbackItemTransaction 中 createdKnown/dropIds 撤销、基线恢复和 replayUserOps；snoozeItem 按 id 查询目标的入口。

现有测试中的“派生 → 编辑/稍后”由窗口期用户操作创建下一期，该创建操作在 userOps 中，可以先重建目标再重放编辑。另一条真实路径不同：下一期由正在提交的原生 ACK 自己创建，它只在 txn.created 中，不在事务前基线和 userOps 的创建记录中。

当用户已对该下一期执行稍后，而原生 ACK 提交失败时，回滚仍无条件删除 txn.created 中的实例。接着重放稍后时，目标既不在基线，也没有用户创建操作能重建；snoozeItem 找不到 id 就返回，用户操作被静默丢弃。

### 独立复现与重载

使用当前 test-regressions.js 的真实 app-core.js、storage.js、createApp/boot/createDisk，只在内存拼接探针，无源码/测试文件修改。

1. 保存 ACK 模式周期事项 A。
2. 执行原生 ACK，扣住提交；界面状态已出现下一期 N。
3. 用户对 N 执行稍后，明确选择三小时后，N=snoozed。
4. ACK 提交失败并回滚；让后续稍后的保存成功。
5. 同一模拟磁盘重启应用。

```text
失败前：items=2，N=snoozed，triggerAt=用户选择
失败后：items=1，N 不存在
重启后：items=1，N 不存在
```

这不是 Q1 修复本身新增加的删除分支，而是现有回滚机制对另一种派生来源仍未覆盖。用户操作过的提醒被移除，后续保存成功也不能恢复它；目前没有提示该操作因依赖失败而未生效。

### 修复建议与验收

明确处理“后续操作依赖失败动作创建的对象”：记录足够的创建来源与快照以保留用户已明确采用的实例，或延迟这类依赖操作直到创建提交结果确定；若业务决定撤销依赖操作，应明确失败反馈，不能成功提示后静默丢弃。仅恢复事务前基线或仅按 id 重放都无法重建本例目标。

补测原生 ACK 派生后的编辑、稍后、完成、删除与 ACK 失败组合，区分用户要求保留、修改和删除，验证提交结果、可见反馈及重载一致性；继续保留用户 ACK 派生的 N1/P1-B 与 Q1 对照。
