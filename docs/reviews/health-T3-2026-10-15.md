## 结论（3 句以内）

- 生命周期主链与三种 8 秒撤销（新建/完成/删除）行为**与基线一致**，R5（撤销后不补响刚取消的那次）在完成/删除撤销路径上有明确实现。
- 唯一 **B 类验收未达标**：B3/AC-05「从提醒点『待整理』同时 ACK + NEEDS_REVIEW」在产品里**没有入口**，提醒（横幅/通知）只有 我知道了/稍后/完成 三个动作。
- 底层动作处理器的**状态守卫只做了一半**：`ack/complete/snooze` 拒绝终态，但 `reopen/restore/stopRepeat/edit` 不拒绝终态或跨状态调用；这些入口目前仅靠 UI 状态门控，不会被普通用户触发（P2 硬化项）。

**矩阵要点：**
1. **due 行**完全符合 §7（我知道了/稍后/完成 语义、计数、状态正确）；`待整理` 缺入口（P1-1）。
2. **计数**：snooze/reopen 重置 `remindCount=0`（`app-items.js:305,414`），`snoozeCount` 逐次 +1；ack/done 不动 snoozeCount —— 与「新一轮」语义一致。
3. **终态守卫**：`ack/complete/snooze` 用 `isTerminal` 拒绝（`app-items.js:303` 等），但 `reopen`（:401）、`restore`（:432）、`stopRepeat`、`applyItemEdit`（:726）**均无守卫** → 见 P2-1。
4. **首页位置**：ack→`#homeActive`（展开可见，`B1x`）；snoozed/waiting→未来页（`fut-row is-snoozed`，`SNOOZE-PILL`）；done/delete→归档；due+NEEDS_REVIEW 仍在 `#homeDue`（INV-02，探针 `REVIEW`）。

## 发现的问题（按严重度排序）

### P1-1 「从提醒点『待整理』」在提醒里没有入口，AC-05 未落地
- **违反条款**：AC-05 · 基线 §7（「待整理 | 从提醒入口点击时同时视为 ACK；进入 NEEDS_REVIEW；不创建重复 Item」）
- **复现步骤**：任一事项到点 → 应用内提醒横幅/系统通知 → 观察可用动作。
- **期望 vs 实际**：期望有「待整理」动作，点击后 `status→acknowledged` 且 `review_status→NEEDS_REVIEW`（不创建重复 Item、不再按「未看到」追击）。实际提醒只有 我知道了/稍后/完成（`app-alerts.js:160-164` 通知动作、`:282-300` 横幅按钮）；「待整理」只存在于**独立的 review 通知**（`managedKind:"review-session"`，动作 `review_snooze/review_skip`，test-smoke L06），且整理确认**不写 ACK**（INV-08，`app-review.js`）。
- **证据**：`lib/app-alerts.js:160-164`、`:282-300`；`test-smoke.js:936-954`。探针无法构造「提醒级待整理」（help/api 无此入口）。
- **影响面**：所有收到到点提醒的用户；到点后想「先收下、晚点再整理」的路径不存在，只能 ACK 或稍后。
- **建议修复**：在提醒通知/横幅动作集加入 `review`（复用 `reviewConfirm` 的 entry：ACK + 置 NEEDS_REVIEW + 不新建 Item）；或明确裁决 AC-05 降级并在基线记录。**验证**：新增 B3 断言——构造 due 项，触发提醒级 review 动作后 `status=acknowledged`、`review_status=NEEDS_REVIEW`、`items.length` 不变。

### P2-1 状态守卫只在 UI 层，底层 `reopen/restore/stopRepeat/edit` 不拒绝终态或跨状态调用
- **违反条款**：INV-03/§7「系统不得推测/越权表态」的守卫一致性；对比 `ack/complete/snooze` 已有 `isTerminal` 守卫。
- **复现步骤**：直接调底层 API（等价于任何绕过 UI 门控的调用）：`app.reopenItem(archivedId)`、`app.restoreItem(waitingId)`、`app.stopRepeat(nonRepeatId)`。
- **期望 vs 实际**：期望终态不接受重开/归档项不被非归档恢复/非周期项不被「停止重复」；实际：`archived` 被 `reopen` 改成 `snoozed`；`waiting/due/...` 被 `restore` 改成 `waiting(triggerAt=null,deadlinePaused)`；**无 repeat 的项** `stopRepeat` 也将其 `archived`。探针矩阵逐格记录了这些。
- **证据**：探针 `M|archived|reopen→snoozed`、`M|waiting|restore→waiting`、`M|waiting|stopRepeat-nonrepeat→archived`；代码 `lib/app-items.js:401`（reopen 无守卫）、`:432`（restore 无守卫）、`stopRepeat`（无守卫）、`:726`（edit 无守卫，可编辑 archived）。
- **影响面**：当前所有入口都在 UI 层按状态显示（reopen 仅 acknowledged、restore 仅 archived、stopRepeat 仅周期项、edit 归档不显示），**普通用户不可达**；风险在后续新增调用面/原生动作时可能绕过。属硬化项，非现网可触发缺陷。
- **建议修复**：给 `rawReopenItem/rawRestoreItem/rawStopRepeat/applyItemEdit` 加与 `isTerminal`/状态相符的前置检查（如 reopen 仅 acknowledged、restore 仅 archived、stopRepeat 需 `repeat.every`）。**验证**：为每个动作补一条「非法状态 → 返回 false 且状态不变」的断言。

### P2-2 编辑已看到/到点项把 `status` 降级为 waiting（观察，非缺陷）
- **说明**：`applyItemEdit` 在「改为未来时间」时把 `due/acknowledged` 降为 `waiting`（`app-items.js:744-745`）。探针 `EDIT|due/acknowledged` 复现。此举使条目离开「已看到未完成」进入未来托管，与 L08/V05「改期开启新一轮」一致，评为**设计选择**，仅记录不判缺陷。
